# 大模型量化实验记录

## INT4 与 SmoothQuant 单层对照

使用 Qwen2.5-1.5B-Instruct 快照 `989aa7980e4cf806f80c7fef2b1adb7bc71aa306` 的第 10 层（从 0 开始编号）`mlp.down_proj`。权重形状为 `[1536, 8960]`，原校准集有 21 个 token，验证集有 25 个 token。误差为输出差值的 Frobenius 范数除以参考输出范数。下表为假量化数值实验，矩阵乘法使用反量化后的浮点张量。

| 配置 | 验证输出相对误差 | 观察 |
| --- | ---: | --- |
| INT4 per-tensor | 83.1694% | 量化后零值比例 96.73% |
| INT4 per-group，组大小 128 | 11.5706% | 零值比例 18.40%，scale 中位数由全局的 0.11830 降至 0.01144 |
| INT4 per-group，组大小 128，加 clipping | 10.7568% | 在原校准集上从 1.0、0.95、0.90、0.80 中选出 0.90，零值比例 16.59% |
| 直接 W8A8 | 11.4718% | 激活按张量、权重按输出通道定标 |
| SmoothQuant W8A8，α=0.5 | 7.8814% | 量化粒度相同，校准激活最大绝对值由 7.8281 降至 1.1641 |

SmoothQuant 缩放前后的 FP32 输出相对误差为 `2.470152e-7`。

### 参考输出检查

`weight_quant/capture_down_proj.py` 保存了权重、两组真实激活和用 FP32 重算的参考输出。原 FP16 层输出与 FP32 参考的相对误差，校准集为 `4.086e-4`，验证集为 `4.033e-4`。用保存的张量在 CPU 重算验证输出，复现误差为 `5.790013e-7`。后续量化对照以这份 FP32 输出为参考。

### INT4 clipping 四档对照

加 clip 的目的是为了判断小权重舍入的更准，能否抵消大权重被截断更多的误差？

固定组大小 128。在每一组里，用「组内最大绝对值 × clipping 比例」决定量化范围。比例只按校准输出误差选择，最终用独立验证集看收益。

| 比例 | 量化后零值比例 | 校准输出相对误差 | 验证输出相对误差 |
| ---: | ---: | ---: | ---: |
| 1.00 | 18.40% | 11.7023% | 11.5706% |
| 0.95 | 17.49% | 11.1004% | — |
| 0.90 | 16.59% | 10.8774% | 10.7568% |
| 0.80 | 14.78% | 11.4789% | — |

全局 INT4 的步长约为 0.1183，绝对值小于约 0.0592 的权重会舍入到零。分组以后，最大的步长只影响它所在的一组，所以零值比例大幅下降。再加一点 clipping 可以让组内刻度更密，但会压低可表示的最大值。比例 0.80 保住了更多小权重，校准输出误差却比 0.90 高。选出的 0.90 在验证集上比无 clipping 降低约 0.81 个百分点。

### SmoothQuant 结果怎么看

`α=0.5` 时，校准激活和权重在每个输入通道上的最大绝对值经过缩放后相等。缩放两边在矩阵乘法里相互抵消，所以 FP32 输出基本一致。平滑后的校准激活最大值从 7.8281 降到 1.1641，共用的激活 INT8 步长随之缩小约 6.7 倍。权重全局最大值则由 0.8281 升到 1.1641，实际权重 scale 仍按输出通道计算。两边的影响合起来，验证输出误差从 11.4718% 降到 7.8814%。

## AWQ 通道缩放

用 `weight_quant/awq_linear.py` 复用完整 `down_proj` 权重、21 个原校准 token 和 25 个原验证 token。按输入通道计算校准激活的平均绝对值，用其 α 次幂生成缩放向量。将缩放后的权重做对称 INT4 假量化，组大小为 128，激活做逆向缩放。α=0 对应普通 per-group RTN。按校准输出误差选择 α。

| α | 校准输出相对误差 | 验证输出相对误差 |
| ---: | ---: | ---: |
| 0.00 | 11.7023% | 11.5706% |
| **0.25** | **10.7629%** | **11.7068%** |
| 0.50 | 11.1996% | — |
| 0.75 | 13.1848% | — |

校准选中的 α=0.25 使校准误差下降 0.9394 个百分点，在独立验证集上相比 RTN 上升 0.1362 个百分点。结果限于这个完整 Linear 层和两组短文本。

## Marlin 风格的 CUDA W4A16 GEMM

在 WSL2 的 RTX 5060 Laptop GPU 上，用 CUDA Toolkit 12.8、`nvcc -arch=sm_120` 编译 `w4a16/marlin_w4a16.cu`。输入为合成 FP16 激活和分组 INT4 权重，输出 tile 为 `16×8`，每 32 个 K 元素为一个量化组。每个 CTA 用一个 warp。

| M × N × K | CTA 数 | 被多个 CTA 拆分的输出 tile | 单个 tile 最多参与的 CTA 数 | 对照结果 |
| --- | ---: | ---: | ---: | --- |
| 16 × 8 × 32 | 1 | 0 / 1 | 1 | 通过 |
| 32 × 24 × 320 | 6 | 0 / 6 | 1 | 通过 |
| 32 × 24 × 320 | 7 | 6 / 6 | 2 | 通过 |
| 32 × 24 × 320 | 26 | 6 / 6 | 5 | 通过 |

四组与程序内的参考计算最大绝对误差均为 0，最后一组另外与 PyTorch 对照，最大绝对误差也是 0。Compute Sanitizer 的同步检查报告 0 个错误。反汇编确认出现了异步拷贝、`LDSM`、`LOP3` 和 `HMMA` 指令。

这组实验可以顺着一个权重理解。打包时先算好哪个线程需要它，运行时该线程从自己的打包字取值，用位运算和半精度算术还原成 MMA 所需的寄存器值。四个共享内存槽轮流装载下一批数据。前两组覆盖单独完成 tile 的情况，后两组验证多个 CTA 交出部分和、由最后到达者归约的路径。指令和正确性已验证，实际流水线重叠程度、共享内存 bank conflict 和加速比留作后续性能实验。

## FP8、NVFP4 与 MXFP4 格式实验

使用 `formats/fp8_scaling.py` 和 `formats/fp4_block_scaling.py`。真实数据对照沿用第 10 层 `down_proj` 和 25 个验证 token。固定激活，只量化权重，再反量化成 FP32 做同一个矩阵乘法。

### FP8 的刻度随数值大小变化

合成样例的最大值为 448 时，INT8 共用的步长为 `448 / 127 ≈ 3.53`，所以绝对值小于约 1.76 的权重会落到零档。E4M3 的外部 scale 恰好为 1。在 `[1, 2)` 内相邻档位相差 0.125，能精确表示 1.125。在 `[64, 128)` 内间距是 8，因此 65 舍入成 64。这个例子展示了浮点指数如何改变**绝对**步长。把末尾的 448 改为 64 后，样例的最大值为 65，INT8 的归零门槛也会降到约 0.256。

### FP4 的分块边界与 scale 舍入

两种 FP4 都用 E2M1，正值档位为 `0、0.5、1、1.5、2、3、4、6`。NVFP4 每 16 个元素共用一个 E4M3 块 scale，再乘 FP32 全局 scale。MXFP4 每 32 个元素共用一个只能取 2 的整数次幂的 E8M0 scale。实验中的 MXFP4 使用 OCP 参考定标规则。

把 `[0.5, 0.75, 1.0, 1.5]` 重复成 64 个元素，只改索引 0 或 16 为 32。三个观察位置 1、17、33 的原值都是 0.75。

| 离群值位置 | NVFP4 块 scale（E4M3） | NVFP4 在 1、17、33 的反量化值 | MXFP4 块 scale | MXFP4 在 1、17、33 的反量化值 |
| --- | --- | --- | --- | --- |
| 无离群值 | `[448, 448, 448, 448]` | `[0.75, 0.75, 0.75]` | `[0.25, 0.25]` | `[0.75, 0.75, 0.75]` |
| 索引 0 | `[448, 20, 20, 20]` | `[0, 0.7143, 0.7143]` | `[8, 0.25]` | `[0, 0, 0.75]` |
| 索引 16 | `[20, 448, 20, 20]` | `[0.7143, 0, 0.7143]` | `[8, 0.25]` | `[0, 0, 0.75]` |

离群值从 0 移到 16，跨过了 NVFP4 的分块边界，所以位置 1 和 17 的结果互换。这两个离群值位置都属于 MXFP4 的第一个 32 元素块，三个观察位置的结果因此相同。MXFP4 的位置 33 在另一个块，仍为 0.75。离群值 32 本身也能保留，例如用 MXFP4 的 `4 × 8` 表示。

**NVFP4 的 0.7143 从哪来？** 有离群值时，全局 scale 是 `32 / (6 × 448) = 1/84`。未包含离群值的块最大值为 1.5，理想块 scale 是 `1.5 / (6 × 1/84) = 21`。E4M3 在这里的相邻档位是 20 和 22，按最近偶数规则，21 舍入到 20。实际有效 scale 就是 `20/84 = 5/21`。0.75 除以它后为 3.15，选中 E2M1 的 3 档，乘回有效 scale 得到 `3 × 5/21 ≈ 0.7143`。这说明 NVFP4 的小块限制了直接影响的范围，公用的全局 scale 仍可能通过块 scale 的舍入轻微影响其他块。

| 格式 | 定标方式 | 反量化后零值比例 | 验证输出相对误差 |
| --- | --- | ---: | ---: |
| INT8 | 整张权重共用一个 scale | 10.4775% | 6.2512% |
| FP8 E4M3 | 整张权重共用一个 scale | 0.0056% | 2.3312% |

## FP8 KV Cache 与单步 Decode Attention

### 写入与追加

`kv_cache/fp8_kv_cache.py` 从 Qwen 第 10 层读取真实 K/V。K 已经过 RoPE，形状为 `[token, KV head, head dim]`，本次验证为 `[31, 2, 128]`。固定方案从另一段 26 token 的校准文本得到 K、V 各一个 FP16 scale，分别约为 0.0234833 和 0.00826263。逐 token、逐 head 方案把每个条目的 K、V scale 一起存进缓存。

先写 28 个真实 token，再逐个追加 3 个真实 token，最后追加一个人为越界条目。两种方案各分配 32 个 token 的容量。

| 指标 | 固定 K/V scale | 每 token、每 KV head 单独定标 |
| --- | ---: | ---: |
| 三个真实追加 token 的饱和数（K / V） | 0 / 0 | 0 / 0 |
| 人为越界条目的饱和数（K / V） | 1 / 1 | 0 / 0 |
| 旧前缀的 FP8 数据和 scale 字节 | 一致 | 一致 |
| 一层分配的 K/V 数据 | 16,384 B | 16,384 B |
| 一层分配的 scale | 4 B | 256 B |

固定 K scale 的覆盖上限约为 `448 × 0.0234833 = 10.52`。人为构造的 K 测试值约为这个上限的两倍，所以写入时会饱和。细粒度方案能单独调大新条目的 scale，旧条目的字节和解释方式都保持一致。比如旧 FP8 值为 128、scale 为 1/32，解码得到 4。如果把共享 scale 改为 1/16，旧字节会解码成 8。逐 token、逐 head 存 scale 的代价是每层每 token 多占 8 B。

### 分开对照 K 与 V 的误差

`kv_cache/fp8_kv_attention.py` 使用同一段真实序列的最后一个 Q，形状为 `[12, 128]`。12 个 Q heads 分两组，每组 6 个，共享缓存中的一个 KV head。四组都读同样的 31 个位置，量化路径使用逐 token、逐 KV head 的 scale，反量化后统一用 FP32 计算 attention。

| 缓存配置 | 各 Q head 的平均概率 TV | 输出相对误差 |
| --- | ---: | ---: |
| 原始 FP16 K/V | 0.0000% | 0.0000% |
| 只量化 K | 3.2003% | 4.9781% |
| 只量化 V | 0.0000% | 1.7528% |
| K/V 都量化 | 3.2003% | 5.2789% |

概率 TV 是每个 head 的概率绝对差之和除以 2。3.2003% 表示平均每个 head 有约 3.20% 的概率质量在 token 之间重新分配。

**分析：**四组对照实验清晰揭示了 $K$ 与 $V$ 量化误差在注意力机制中的不同传播路径与敏感度差异：

- 仅量化 $V$ 时，由于注意力权重 $P = \text{softmax}(QK^T/\sqrt{d})$ 与 $V$ 无关，概率分布保持严格零误差（`mean TV = 0.0000%`），量化噪声仅在随后的线性加权求和 $O = P\hat{V}$ 中引入，受凸组合平滑效应抑制，最终输出相对误差仅为 `1.7528%`；
- 而仅量化 $K$ 时，误差直接进入 $QK^T$ 点积并经 $\text{softmax}$ 指数非线性放大，导致注意力权重分布发生明显偏移（`mean TV = 3.2003%`），进而造成加权错配，使输出相对误差飙升至 `4.9781%`（约为仅量化 $V$ 的 2.8 倍）；
- 当 $K$ 与 $V$ 同时量化时，概率偏移仍完全由 $K$ 主导（`3.2003%`），总输出相对误差（`5.2789%`）则近似呈两路独立误差的正交叠加（$\sqrt{4.9781\%^2 + 1.7528\%^2} \approx 5.2777\%$），从而实证了 **$K$ 对量化的敏感度显著高于 $V$**。

**补充**：V 的误差是按注意力权重取平均，能否减小取决于误差方向和落在哪些 token 上。高注意力 token 的误差如果方向一致，仍会保留下来。Softmax 对所有 logits 的共同偏移保持不变，真正改变概率的是 token 之间的相对分数。K/V 同时量化时，除了只改 K 的 `ΔP @ V` 和只改 V 的 `P @ ΔV`，还有两者共同变化的 `ΔP @ ΔV`。这次两个数值很接近，单凭这一点无法判断误差是否正交。K 更敏感的观察限于这层、这段输入和当前定标方式。

### Triton 直接读取 FP8 缓存

`kv_cache/fp8_kv_decode_triton.py` 每个 Triton program 处理一个 Q head，通过 GQA 映射找到自己共享的 KV head。沿历史 token 每 16 个位置读一个 tile，读取原始 E4M3 字节和 FP16 scale，在 kernel 内反量化。在线 softmax 保存截至当前 tile 的最大 logit、分母和 V 的加权和。如果最大值更新，先把旧分母和旧加权和乘上同一个换算因子，再加入新 tile 的贡献，最后用加权和除以分母。

PyTorch 参考使用同一份 FP8 字节、同一份 scale 和同一个 Q，先恢复整个有效前缀再计算 attention。下面的误差比较的是两种计算路径，前一节表格比较的是量化前后的差异。

| 有效长度 / 分配容量 | 输出形状 | 覆盖情况 | 和 PyTorch 参考的最大绝对误差 |
| --- | --- | --- | ---: |
| 1 / 34 | `[12, 128]` | 单位置和掩码 | `0.000000e+00` |
| 16 / 34 | `[12, 128]` | 一个完整 tile | `7.152557e-07` |
| 31 / 34 | `[12, 128]` | 两个 tile，最后一个带掩码，包含新追加的 token | `3.576279e-07` |

三组均通过 `rtol=1e-4, atol=1e-5` 的校验。Triton 路径每次只反量化当前 tile，PyTorch 参考显式恢复整个前缀。此处测的是正确性。

手写的 Triton 版本复现了这三组结果。31 个位置会跨两个 tile，Triton 在线更新最大值、分母和加权和，PyTorch 先计算完整前缀的分数再统一计算 softmax。两条路径的归约顺序和指数运算可能不同。16 个位置只有一个 tile，也出现了微小差异，因此不能仅凭这些结果把差异都归到跨 tile 归约，或把误差固定说成 1 ULP。一个有效位置时，softmax 权重为 1，本次输出与反量化的 V 完全一致。

| FP16 K/V 对照（折算） | 31,744 B | 34,816 B |

#### 一、计算前的四组已知条件

1. **模型结构（Qwen2.5-1.5B）**
   - `kv_heads = 2`，每层有 2 个 KV heads。
   - `head_dim = 128`，每个 head 的向量维度是 128。
   - `num_layers = 28`，全模型有 28 层。
2. **缓存长度**
   - 已填充的有效 token 数 `occupied = 31`。
   - 总预分配容量 `allocated = 34`。
   - 闲置空位 `unused = 34 - 31 = 3`。
3. **单个元素的字节数**
   - `float8_e4m3fn`（FP8 数据）占 **1 B**。
   - `float16`（FP16 基准与 scale）占 **2 B**。
4. **单位换算**
   - `1 KiB = 1,024 B`。

#### 二、算清单层一个 token 占多少字节

每层每个 token 都要存 K 和 V 两份数据。先算一份，再乘以 2。

**FP8 缓存**

- **K 数据本体。** 形状是 `[kv_heads, head_dim]`，共有 `2 × 128 = 256` 个元素。每个 FP8 元素占 1 B，所以 K 数据占 **`256 × 1 = 256 B`**。
- **K scale。** 每个 KV head 配一个 scale，形状是 `[kv_heads]`，共有 2 个元素。每个 FP16 scale 占 2 B，所以 K scale 占 **`2 × 2 = 4 B`**。
- **K 合计。** `256 + 4 = 260 B`。
- **V 合计。** V 同样有 `256 B` 的数据和 `4 B` 的 scale，合计 `260 B`。
- **一层每 token 的 FP8 K/V 合计。** `260 × 2 = 520 B`，对应输出的 `FP8=520 B`。

**FP16 基准**

- **K 数据。** 同样有 `2 × 128 = 256` 个元素，每个 FP16 元素占 2 B，所以 K 占 `256 × 2 = 512 B`。这个基准直接保存 FP16 值，无需额外存 scale。
- **V 数据。** V 同样占 `512 B`。
- **一层每 token 的 FP16 K/V 合计。** `512 × 2 = 1,024 B`，对应输出的 `FP16=1,024 B`。

#### 三、乘以 token 数，逐项核对测试输出

**已填充的 31 个 token（`occupied`）**

-  `520 B/token × 31 = 16,120 B`。
- FP16 折算：`1,024 B/token × 31 = 31,744 B`。

**预分配的 34 个位置（`allocated`）**

-  `520 B/token × 34 = 17,680 B`。
- FP16 折算：`1,024 B/token × 34 = 34,816 B`。

**闲置的 3 个位置（`Unused FP8 slots`）**

- 用预分配减去已使用：`17,680 - 16,120 = 1,560 B`。

#### 四、从单层推算到全模型 28 层

上面的表格对应第 10 层。按同样的缓存布局推算全模型，每 token 的用量乘以 28

1. **FP16 全模型每 token**
   - 单层占 `1,024 B`，28 层占 `1,024 × 28 = 28,672 B`
   - 换成 KiB：`28,672 ÷ 1,024 = 28 KiB/token`
2. **FP8 全模型每 token**
   - **K/V 数据本体。** 单层占 `256 + 256 = 512 B`，28 层占 `512 × 28 = 14,336 B`，即 `14,336 ÷ 1,024 = 14 KiB/token`。
   - **Scale 元数据。** 单层占 `4 + 4 = 8 B`，28 层占 `8 × 28 = 224 B/token`。从数量直接算，就是 `2 份（K 和 V）× 28 层 × 2 个 KV heads × 2 B（FP16）= 224 B`。
   - **FP8 合计。** `14,336 + 224 = (512 + 8) * 28 = 14,560 B/token`，约 `14.22 KiB/token`。
3. **最终比例**
   - Scale 元数据占 FP8 K/V 数据本体的比例为 `224 ÷ 14,336 = 0.015625 ≈ 1.56%`。
   - FP8 缓存总量占 FP16 的比例为 `14,560 ÷ 28,672 ≈ 50.78%`，即节省约 **49.22%** 的 KV 缓存空间。

单层表中的 FP8 分配值来自四个张量的实际存储，全模型数值由相同布局按层推算。GPU 进程显存还包含分配器、模型和运行时等开销。
