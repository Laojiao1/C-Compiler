# 学习路线

## 阶段一：C++ 核心工程
**目标**：摆脱 Python 的思维定势，跨越 C++ 的内存管理大关，并具备工业级的高并发编程能力。不要浮于表面，必须亲自动手“造轮子”。

**预计时间**：2 - 3 周

**核心知识点**：

1. **现代内存模型与 RAII**：搞懂左值/右值引用、`std::move`。彻底理解 RAII（资源获取即初始化）机制，这是 C++ 不依赖垃圾回收（GC）也能安全管理内存的核心哲学。
2. **手写智能指针 (硬核必做)**：不要只学理论！自己定义类实现简易版的 `std::unique_ptr` 和 `std::shared_ptr`。
   - *难点*：
   - 彻底搞懂引用计数（Reference Counting）在哪里增加和减少
   - 如何重载 `*` 和 `->` 运算符
   - 如何正确处理拷贝构造函数与移动赋值函数。
3. **高并发编程与线程池 (硬核必做)**：掌握 `std::thread`, `std::mutex`, `std::condition_variable`。
   - *难点*：在 TVM 或底层算子调度中，线程池是标配。你必须手写一个 Thread Pool，理解“任务队列”和“生产者-消费者”模型，搞懂如何通过条件变量唤醒空闲线程。
4. **LRU Cache (数据结构大考)**：结合哈希表 `std::unordered_map`（负责 O(1) 查找）和双向链表 `std::list`（负责 O(1) 插入和删除），自己造一个高频面试考点 LRU 缓存。

**推荐教程/资源**：
*   **视频（强烈推荐）**：B站搜索 **“侯捷 C++ 面向对象高级编程”（上下两部）**。讲透内存模型和面向对象。
*   **代码参考（线程池）**：Github 搜索 `progschj/ThreadPool`。这是一个不到 100 行的经典 C++11 线程池，逐行抄一遍并理解。
*   **实战靶场（LRU）**：LeetCode 第 146 题 (LRU 缓存)，强制自己只用 C++ 提交直到击败 90% 以上用户。
*   **书籍（当字典查）**：《Effective Modern C++》（重点看智能指针和右值引用的条款）。

## 阶段二：编译器级 OOP 与跨语言桥梁
**目标**：掌握 AI 框架（如 PyTorch、TVM）底层的代码架构模式，彻底打通 C++ 与 Python 的生态壁垒，让你的 C++ 算子能在 PyTorch 中跑起来。

**预计时间**：2 周

**核心知识点**：
1. **高频设计模式 (重点关注 Visitor)**：
   - **访问者模式 (Visitor Pattern)**：AI 编译器核心中的核心。无论你是在 TVM 里遍历 TensorIR，还是在 PyTorch 里遍历 `torch.fx` 的抽象语法树，全都靠 Visitor。
   - **工厂模式 (Factory Pattern)**：用于底层算子库的动态注册机制（比如根据不同硬件动态调起不同的算子）。
2. **泛型编程 (Templates)**：掌握类模板与函数模板。不需要学深奥的元编程，但必须能看懂。因为优秀的算子代码（比如 Triton 的 C++ 后端）通常是模板化的，为了用同一套代码兼容 FP32/FP16/INT8 等不同数据类型。
3. **PyBind11 跨语言通信 (极其重要！)**：这是你从纯 C++ 工程师跨越到 AI Infra 工程师的唯一桥梁。你需要知道如何将 C++ 变量/矩阵转换为 Python 的 Numpy/Tensor 对象。
4. **编译器 IR / Pass 基础 (衔接后续加速器编译栈)**：
   - 从普通 AST 进一步升级到计算图 / IR 思维，理解 Node、Edge、DAG、Tensor metadata。
   - 学会写最小版 Pass Manager，并实现 Constant Folding、Dead Code Elimination、Operator Fusion、Shape / dtype / device inference。
   - 理解 Pattern Rewrite：不要只会遍历 IR，还要能识别模式并替换子图，这是后续做算子融合、图优化、硬件后端 lowering 的基础。

**推荐教程/资源**：
*   **图文网站（设计模式）**：[Refactoring.guru - 访问者模式](https://refactoringguru.cn/design-patterns/visitor)（图解非常棒，生动易懂）。
*   **视频（泛型编程）**：B站搜索 **“侯捷 C++ STL 体系结构与内核分析”**，顺带就能把泛型和模板领悟了。
*   **官方文档（必看）**：[PyBind11 官方文档 - First Steps](https://pybind11.readthedocs.io/en/stable/basics.html)。写一个极简的 C++ 加法函数，用它打包给 Python 调用。
*   **开源代码库**：Github 搜索 `pytorch/extension-cpp`，学习 PyTorch 官方推荐的 C++ 自定义算子扩展写法。
*   **编译器补充（进阶）**：阅读 TVM / MLIR / PyTorch FX 的 IR 与 Pass 相关资料。此阶段不要求啃完整源码，但必须能理解“图 -> IR -> Pass -> Lowering -> Runtime”的主链路。

**当前完成状态（已达标，可进入阶段三）**：
1. **TVM 入门已完成**：
   - 已粗略了解 TVM 架构，以及两层 IR：Relay IR、TensorIR。
   - 已通过 Docker 搭建 TVM 环境。
   - 已用 TVM Schedule 对 GEMM 做过简单优化，包括内存重排、分块计算、累加优化，让矩阵乘法跑得更快。
   - 已将训练好的模型导出为 ONNX，并通过 TVM 现有工具完成简单编译优化和运行。
2. **阶段二判断**：
   - 当前 TVM 掌握程度属于“概念 + 入门实战级”，已经足够支撑进入阶段三。
   - 暂时不需要停下来深入 TVM 源码、MLIR 或完整 Pass 框架。
   - 阶段四完成后，系统回补 TVM TensorIR、Schedule 和 Lowering；BYOC 先理解扩展边界，等阶段六接触真实后端项目时再深入，不为“学完 TVM”一次性啃完全部内容。

## 阶段三：算子性能模型与 Triton/GPU 实战
**目标**：在扎实的 C++ 系统架构底盘上，建立可迁移的算子性能模型。GPU/Triton 是训练场，核心不是只会写 Triton 语法，而是理解 Tiling、访存复用、带宽瓶颈、并行划分和 Benchmark 证据；这些能力后续可以迁移到实验室 FPGA 深度学习加速器和其他异构后端。

**预计时间**：4 - 6 周

**阶段三执行原则**：
阶段三的六大知识点不是线性前置条件，不需要全部学完再写代码。它们是围绕六个算子项目逐步展开的知识地图。

正确顺序是：
```text
01_vector_add
  只需要先学 Triton 最小语法、block、mask、load/store、GB/s

02_softmax
  再补 reduction、数值稳定性、片上复用

03_matmul
  再补 tiling、tl.dot、Tensor Core、TFLOPS

04_layernorm
  再补 reduction + elementwise fusion、register pressure

05_attention_naive
  再补 Attention 计算图、中间矩阵代价

06_flash_attention_forward
  最后综合 online softmax、tiled attention、SRAM/register 复用
```

因此当前第一步不是系统学习完所有 GPU 理论，而是先完成 `Triton/01_vector_add/` 的正确性、benchmark 和笔记闭环。

**核心知识点**：
1. **GPU 性能模型 (先知道瓶颈在哪里)**：
   - 彻底搞懂核心概念：**SM (流式多处理器)**、**Warp (线程束)**、Occupancy、Register Pressure。
   - 深刻理解存储层级：**Global Memory (全局显存)**、**L2 Cache**、**Shared Memory/SRAM**、Register。
   - **生死线知识**：彻底搞懂什么是**访存合并 (Coalesced Memory Access)**，以及为什么 stride、alignment、连续内存会直接决定带宽利用率。
   - 建立 Roofline 思维：判断一个算子是 **memory-bound** 还是 **compute-bound**，并用 GB/s、TFLOPS、理论峰值百分比解释性能。
2. **Triton 编程模型 (从线程思维切换到 Blocked Program 思维)**：
   - 掌握 `@triton.jit`、`tl.program_id`、`tl.arange`、`tl.load`、`tl.store`、mask、stride、block size。
   - 理解 Triton 的核心抽象：一个 program instance 负责一个 block，而不是手动管理每个 CUDA thread。
   - 学会阅读生成的性能现象：block 太小会调度开销大，block 太大会寄存器压力高，mask 会影响边界处理但不能乱用。
3. **官方三板斧 (必须手写 + Benchmark)**：
   - `Vector Addition`：理解 block 切分、mask、连续访存、理论带宽。
   - `Fused Softmax`：理解 row-wise reduction、数值稳定性、SRAM/寄存器复用，避免反复读写 global memory。
   - `Matrix Multiplication`：理解 `BLOCK_M/N/K`、tiling、accumulator、`tl.dot`、Tensor Core、不同 shape 下的性能差异。
4. **Benchmark 与性能诊断 (算子优化必须有证据)**：
   - 每个算子至少对比三版：PyTorch baseline、Triton naive、Triton optimized。
   - 每个 benchmark 必须输出：耗时、GB/s 或 TFLOPS、speedup、correctness check (`torch.allclose`)。
   - 学会使用 `triton.testing.do_bench`、`@triton.testing.perf_report`，并记录不同 block size、num_warps、num_stages 的影响。
5. **PyTorch Extension 衔接 (从裸 kernel 到工程算子)**：
   - 从 PyBind11/NumPy 过渡到 `torch::Tensor`，理解 contiguous、stride、dtype、device、storage、lifetime。
   - 跑通一个 PyTorch C++/CUDA custom op，重点不是深挖 CUDA 语法，而是理解 Python -> Dispatcher -> Tensor -> Kernel 的调用链。
   - 为后续算子做 dtype dispatch 和 device dispatch 的工程准备。
6. **大模型算子实战：简化版 FlashAttention**：
   - 先写 naive attention：显式计算 `QK^T`、softmax、再乘 `V`，作为正确性基线。
   - 再写 tiled attention forward：不显式 materialize `QK^T`，理解 online softmax 的 `m_i` / `l_i` 更新。
   - 分阶段支持：固定 shape -> causal mask -> fp16/bf16 -> benchmark 对比 PyTorch SDPA -> 再考虑 backward。

**建议项目结构**：
```text
Triton/
  01_vector_add/
    kernel.py
    test_correctness.py
    benchmark.py
    notes.md
  02_softmax/
  03_matmul/
  04_layernorm/
  05_attention_naive/
  06_flash_attention_forward/
  benchmarks/
  notes/
```

**项目目录与知识点对应关系**：
1. **`01_vector_add/`：Triton 执行模型与基础访存**
   - 对应知识点：`tl.program_id`、block 切分、`tl.arange`、`tl.load` / `tl.store`、mask 边界处理。
   - 性能重点：这是典型 memory-bound 算子，重点计算 GB/s，理解连续访存和访存合并。
   - 学习目的：理解一个 Triton program instance 如何负责一块数据，而不是从 CUDA thread 视角手动管理每个线程。
2. **`02_softmax/`：Reduction、数值稳定性与片上复用**
   - 对应知识点：row-wise reduction、`max` / `sum` 规约、数值稳定 softmax、SRAM / register 复用。
   - 性能重点：避免把中间结果反复写回 global memory，理解 fused softmax 为什么能快。
   - 学习目的：为后续 FlashAttention 的 online softmax 打基础。
3. **`03_matmul/`：Tiling、Tensor Core 与 compute-bound 分析**
   - 对应知识点：`BLOCK_M/N/K`、tiling、accumulator、`tl.dot`、num_warps、num_stages。
   - 性能重点：这是典型 compute-bound 算子，重点计算 TFLOPS，并分析不同 shape / block size 对性能的影响。
   - 学习目的：建立 GEMM 性能模型；后续 Conv、Attention、MLP 都绕不开 MatMul。
4. **`04_layernorm/`：Reduction + Elementwise Fusion**
   - 对应知识点：均值、方差、归一化、elementwise 操作融合、register pressure。
   - 性能重点：尽量用一次读写完成多步操作，理解算子融合为什么能减少 global memory traffic。
   - 学习目的：训练真实模型中高频非 GEMM 算子的优化思路。
5. **`05_attention_naive/`：Attention 正确性基线**
   - 对应知识点：`QK^T`、softmax、`P @ V`、中间张量生命周期。
   - 性能重点：显式 materialize `QK^T` 会造成巨大显存占用和访存压力。
   - 学习目的：作为 FlashAttention 的 correctness baseline，先把 Attention 计算图彻底吃透。
6. **`06_flash_attention_forward/`：阶段三综合项目**
   - 对应知识点：tiled attention、online softmax、`m_i` / `l_i` 更新、SRAM / register 复用、hardware-aware algorithm。
   - 性能重点：不显式生成完整 `QK^T`，通过分块和在线归一化降低显存流量。
   - 学习目的：综合 MatMul、Softmax、Tiling、Benchmark，完成一个真正有含金量的大模型算子。
7. **`benchmarks/`：通用性能工具**
   - 放通用 benchmark 函数、GB/s 计算、TFLOPS 计算、PyTorch baseline 对比、结果表格输出。
   - 每个算子的性能结论都必须来自这里的可复现实验，而不是主观感觉。
8. **`notes/`：性能模型与复盘**
   - 放阶段三总笔记，例如 GPU 性能模型、访存合并、Roofline、Triton 调参、GPU vs FPGA 后端对比。
   - 这里不是可选项。这个方向不能只写代码，必须能解释性能。

**每个算子的完成标准**：
1. 正确性：至少覆盖普通 shape、非 2 的幂 shape、边界 mask、不同 dtype。
2. 性能：必须和 PyTorch baseline 对比，并能解释快在哪里、慢在哪里。
3. 笔记：`notes.md` 里必须写清楚访存量、计算量、瓶颈判断、block size 选择理由。
4. 复盘：每次优化只改一个变量，例如 `BLOCK_SIZE`、`num_warps`、`num_stages`，避免盲调。

**推荐教程/资源**：
*   **视频（GPU架构）**：谭升的 CUDA 教程。**注意**：阶段三暂时不深入 CUDA C++，优先借助 Triton 提高 GPU Kernel 编程的抽象层级并建立算子性能模型；阶段四再系统学习 CUDA，把 Triton 编译器隐式完成的线程组织、访存、同步和 Tensor Core 映射显式写出来。
*   **官方文档（Triton）**：[Triton 官方 Tutorials](https://triton-lang.org/main/getting-started/tutorials/index.html)。必须按顺序手敲 Vector Addition、Fused Softmax、Matrix Multiplication、LayerNorm、Fused Attention。
*   **官方文档（PyTorch Extension）**：[PyTorch Custom C++ and CUDA Operators](https://docs.pytorch.org/tutorials/advanced/cpp_custom_ops.html)。至少跑通一个 `torch::Tensor` 自定义算子。
*   **进阶论文**：阅读 Tri Dao 的 FlashAttention 论文，搞懂硬件感知（Hardware-Aware）算法、分块（Tiling）和 online softmax 的数学原理。
*   **性能工具**：优先学会用 `torch.cuda.Event`、`triton.testing.do_bench`、Nsight Systems / Nsight Compute 的基础用法。先能看懂 kernel time、memory throughput、occupancy，再谈深入调优。

## 阶段四：Triton 编译映射与 CUDA Attention 深入

**目标**：阶段三解决“会写、会测、会优化 Triton 算子”，阶段四继续回答两个更底层的问题：Triton 编译器如何把 blocked program 映射到 GPU 线程、Warp、共享内存和机器指令；同一个算子改用 CUDA C++ 后，性能策略如何显式落到线程组织、访存、同步和 Tensor Core 上。

**定位**：这是算子开发方向的必修阶段，也是连接“算子优化”和“编译器后端”的关键桥梁。不要在阶段三之前展开，以免同时被 Triton 语法、CUDA 线程模型和编译器 IR 三套抽象拖慢。

**建议执行顺序**：
```text
4.0 补 CUDA 映射最小前置：grid / block / thread / warp、线程索引、存储归属和线程视角的合并访存
4.1 以阶段三已经写熟的 vector_add / softmax / matmul 作为观察样本追踪 Triton 编译链和每一层 IR 的语义变化
4.2 系统学习 CUDA C++ 最小必需集，并重写 vector_add / reduction / softmax
4.3 从 naive GEMM 逐步优化到 tiled GEMM、register blocking 和 Tensor Core
4.4 拆解 Attention：QK^T -> Softmax -> P@V -> fused/tiled attention
4.5 实现并分析简化 CUDA Attention Forward
4.6 用 Nsight Compute 和生成指令解释 Triton 版与 CUDA 版的性能差异
```

`4.0` 只建立阅读 TTGIR 所需的硬件坐标系，并用一个最小 CUDA Vector Add 对照 `blockIdx.x`、`threadIdx.x` 与 Triton Program。此时不展开 CUDA Softmax、GEMM、Attention、复杂共享内存优化或 Tensor Core 编程；这些内容仍放在 Triton lowering 之后。

**核心知识点**：
0. **CUDA 映射最小前置**：

- 理解 `grid -> block/CTA -> warp -> thread` 的执行层次，能读懂 `blockIdx.x`、`threadIdx.x`、`blockDim.x` 和 `gridDim.x`。
- 建立初步对应：一个 Triton Program 通常映射为一个 GPU CTA，但 Triton Program 不等于 CUDA Thread，`BLOCK_SIZE` 也不等于 CUDA 线程数。
- 理解寄存器由线程私有、Shared Memory 由同一 Block/CTA 共享、Global Memory 由整个设备访问。
- 从线程视角理解合并访存：不仅要看逻辑地址连续，还要看同一条访存指令中相邻线程实际访问的地址。
- 只写一个最小 CUDA Vector Add 作为映射参照，不在此处进行复杂 CUDA 优化。

1. **Triton 到 GPU 指令的映射**：
   - 建立主链路：Python DSL / JIT AST -> Triton IR（TTIR）-> TritonGPU IR（TTGIR）-> LLVM IR -> PTX -> cubin / SASS。
   - TTIR 重点看算子语义和张量级数据流；TTGIR 重点看 layout、线程/warp 分配、shared memory、layout conversion；PTX/SASS 重点确认最终 load/store、shuffle、barrier、MMA 等指令是否符合预期。
   - 学会保存并阅读一个小 kernel 的各层 IR，对照 `tl.program_id`、`tl.arange`、`tl.load`、reduction、`tl.dot` 分别被 lowering 成什么。
   - 理解编译器不是机械翻译语法，而是在做 layout propagation、coalescing、shared-memory allocation、instruction selection 和目标架构相关 lowering。
2. **CUDA C++ 最小必需集**：
   - thread / warp / block / grid 映射，global/shared/register memory，barrier，warp shuffle，向量化访存和 bank conflict。
   - 掌握必要的 stream、event、异步拷贝与 kernel launch；暂时不追求把 CUDA API 全部学完。
   - 学会检查资源使用：registers per thread、shared memory per block、occupancy、memory throughput、warp stall reason。
3. **GEMM 优化阶梯**：
   - `naive` -> global-memory coalescing -> shared-memory tiling -> register blocking -> double buffering / software pipeline -> vectorized load -> Tensor Core。
   - Tensor Core 分三层推进：先理解 tile、dtype、layout 和硬件映射要求；再用 WMMA 或较高层接口跑通 correctness 与 benchmark；最后阅读 PTX MMA、CUTLASS / CuTe 的实现思路。
   - 首轮目标是能解释 Tensor Core mapping，不要求直接手写 `ldmatrix`、`mma.sync`、复杂 swizzle 或接近 CUTLASS 水平的极致 GEMM。
   - 每一步只改变一个主要策略，记录适用 shape、资源消耗、TFLOPS 和相对 cuBLAS 的峰值百分比。
   - 目标不是手写超过 cuBLAS，而是能解释库实现为何需要分块层次、流水和数据布局。
4. **Softmax 优化阶梯**：
   - `naive multi-kernel` -> row-wise 单 block -> warp shuffle reduction -> shared-memory reduction -> fused scale/mask/softmax。
   - 正确处理减最大值、FP32 accumulation、非 2 的幂长度、长序列跨 block 情况。
   - 对比不同序列长度下带宽、launch 次数、同步开销和 occupancy 的变化。
5. **CUDA Attention 综合实战**：
   - 在 05_cuda_attention/ 中实现 Unfused Attention 基线与 Tiled Online FlashAttention Forward，对比二者的正确性、Kernel 时间、启动次数及中间矩阵 S/P 的全局内存读写代价。
   - 重点在于把已经完成的 GEMM、融合 Softmax 与 Online Softmax 组合为完整 Attention 数据流。

**建议项目结构**：

## 阶段五：大模型推理系统与多卡优化

**目标**：从“一个 kernel 如何变快”扩展到“一个模型服务如何在一张或多张 GPU 上获得更好的吞吐、时延和显存利用率”。核心不是会启动 vLLM/SGLang 命令，而是理解调度、KV Cache、并行策略、通信和算子库之间的边界。

**定位**：这是面向大模型推理系统、算子与异构后端岗位的重要拓展线。阶段五内容很宽，必须分层：5.1～5.4 是单卡必修主线，5.5～5.6 是多卡必修主线，5.7 是进阶优化，5.8 的 PD 分离是资源允许时的综合项目。它不是进入实验室 FPGA 项目的硬前置，可以与阶段六并行。

**执行原则**：

1. 单卡源码学习以 **nano-vLLM** 为主线，真实 vLLM 按需对照；SGLang 留到 prefix-aware scheduling 与 PD 分离时横向比较。
2. 固定框架 commit / 版本、模型、dtype、GPU、CUDA、驱动和启动参数。框架迭代很快，所有源码笔记都记录版本。
3. 每个实验先写假设，再做控制变量 benchmark，最后用 profiler、日志或源码解释结果；不能只凭 tokens/s 下结论。
4. 区分离线推理与在线 serving。离线看最大吞吐，在线看给定到达率和 SLO 下的 latency、goodput 与尾延迟。

**必须先建立的推理性能模型**：

1. **Transformer 单层执行结构**：先以 GPT-2 的 LayerNorm、QKV projection、learned positional embedding、causal MHA、output projection、GELU MLP、residual、LM head 与 sampling 建立完整执行链；进入现代模型时，再对照 RMSNorm、RoPE、GQA/MQA、SwiGLU 与 MoE 的差异。能写出 Prefill 和单 token Decode 时各 GEMM 的主要 shape。
2. **Prefill 与 Decode**：Prefill 通常更偏计算密集；Decode 的 GEMM 更窄，且需要持续读取历史 KV Cache，通常更受显存带宽、batch size 和调度影响。不能把这个经验判断当定律，必须结合 arithmetic intensity 和 profiler 验证。
3. **显存账本**：分别估算权重、KV Cache、activation/workspace、CUDA Graph 和通信 buffer。对标准 MHA，单请求 KV Cache 元素量可按 `2 × num_layers × sequence_length × num_kv_heads × head_dim` 估算，再乘 dtype 字节数；GQA/MQA 使用 `num_kv_heads`，不是 `num_attention_heads`。
4. **服务指标**：理解 TTFT、ITL、TPOT、端到端 latency、request/token throughput、并发、KV Cache 利用率、prefix cache hit rate；报告分布、样本量和测量边界，而不是只给平均值。样本足够时报告 p50/p95/p99，不能把少量样本计算出的 p99 当作可靠的尾延迟结论。

### 5.1：GPT-2 单卡推理链与性能基线

1. **模型结构与手写前向**：Token/位置嵌入、Pre-LN、因果多头 Attention、MLP/GELU、残差与 LM Head；理解主要张量 shape、Conv1D 权重布局及 Embedding/LM Head 权重共享（`model.py`）。
2. **权重加载与数值对齐**：加载 Hugging Face GPT-2 权重，检查参数对应关系，用 FP32 logits 与参考模型比较误差（`tests/test_model.py`）。
3. **Prefill 与三条 Decode 路径**：理解首 Token 生成、位置偏移和逐层 KV；实现无缓存、`torch.cat` 追加、预分配原地写入，并校验三条路径的 Token 与 logits（`decode.py`、`tests/test_decode.py`）。
4. **显存与计算模型**：估算权重、KV Cache、logits 和临时张量容量，对照 allocated/reserved 与峰值测量；理解 Prefill/Decode 的计算与访存差异（`measure_memory.py`、`docs/memory_model.md`）。
5. **Benchmark 与性能分析**：固定环境、输入和计时边界，理解预热、CUDA 同步、Prefill/Decode 延迟、吞吐与显存统计；结合 Nsight Systems 时间线区分 kernel、CPU launch 与同步开销（`benchmarks/benchmark_decode.py`、`benchmarks/benchmark_sweep.py`、`profiles/`）。
6. **算子接入与端到端评估**：将 OperatorEngine 接入 Prefill Attention，理解 Q/K/V 布局与连续化、数值容差和生成分叉，以及局部算子性能与端到端收益的区别；明确当前接口不支持直接替换 Decode Attention（`benchmarks/benchmark_operatorengine.py`、`docs/report.md`）。
7. **现代模型结构对照**：以 GPT-2 为参照理解 RoPE、RMSNorm、GQA/MQA、SwiGLU 与 MoE 的结构、KV 容量和计算变化，只做概念对照，不另写完整模型。

### 5.2：单卡 serving 与严谨 benchmark

1. **服务基准基础**：离线与在线的区别、请求生命周期、ISL/OSL、到达率、并发、指标定义与计时边界。
2. **离线吞吐基线**：精确 Token 输入、采样参数、预热与重复测量、整批计时、吞吐计算及请求规模曲线。
3. **在线服务调用**：启动 vLLM 服务，使用现成客户端或辅助示例完成一次流式请求，理解请求进入引擎、正文返回与完成判断；不要求自行实现完整客户端。
4. **性能指标与测量边界**：读懂吞吐、TTFT、TPOT 和端到端延迟，理解排队的影响，区分文本块与 Token、客户端观察时间与服务端内部时间。

负载发生器、系统压测和完整 SLO/尾延迟报告不作为本节必做任务；后续研究调度、缓存或源码中的具体问题时，再选用相应工具与实验。

### 5.3：KV Cache 与请求调度

1. **Paged KV Cache：布局、块管理、前缀复用与分页读取**：
   - 从模型各层的 K/V shape 和每 Token 显存量出发，理解 Token slot、逻辑块、物理块、block table、内部/外部碎片，以及分配、追加、引用计数、回收、淘汰和 prefix hash。
   - 逐步实现一个教学级块管理模型，并用 PyTorch reference 验证通过 block table 从非连续物理块恢复的逻辑连续 K/V，与连续存储 K/V 的 Attention 结果一致；不实现生产级 KV Cache Manager，也不手写 GPU Paged Attention kernel。
2. **请求调度：Continuous Batching、Token Budget 与抢占**：
   - 理解 waiting、running、finished 请求的状态变化，以及 continuous batching、`max_num_seqs`、`max_num_batched_tokens`、KV Cache 容量、`max_model_len`、chunked prefill、decode priority 和抢占如何共同决定每一步的 batch formation。
   - 沿用前述教学模型增加调度轨迹，记录每一步的 Prefill/Decode Token 数量、Token budget 使用量、KV Block 占用和请求状态，不提前展开 5.4 的完整源码主链。
3. **三个控制变量实验与阶段总结**：
   - 分别控制 `max_num_batched_tokens` 与 chunked prefill，观察长 Prefill 与 Decode 共存时吞吐、TTFT 和 TPOT 的相互牵制。
   - 使用容量公式预测 KV Cache 容量与并发的关系，再选择少数边界点进行验证，不重复请求规模扫描。
   - 使用独立的共享前缀 workload，验证 prefix caching 对 prefix cache hit rate、TTFT 和吞吐的影响；与普通性能基线严格隔离，避免重复 prompt 意外污染结果。
   - 实验完成后分别整理理论讲义与实验记录，保留实际配置、完整命令、原始结果、结论边界和未验证事项。

### 5.4：nano-vLLM 实现主线与 vLLM 源码对照

以 nano-vLLM 为主线，结合已掌握的整体架构补齐代码细节；真实 vLLM 使用固定版本，围绕关键机制按需对照。

1. **请求与调度实现**：
   - 沿 nano-vLLM 的引擎循环、Sequence、Scheduler 和 BlockManager，追踪请求状态、计算进度、块分配、前缀复用、抢占与回收，理解关键分支及其状态约束。
2. **从调度到 GPU 执行**：
   - 深入 ModelRunner 的输入准备、input_ids、positions、slot mapping 和 block table，再连接模型层、KV 写入、Attention 与 Linear/GEMM 调用，理解调度决定怎样落实为实际计算。
3. **真实 vLLM 关键机制对照**：
   - 以固定版本官方源码为依据，对照一轮工作表达、计算进度更新时点、缓存引用、抢占恢复与延迟释放等关键机制，能解释差异并指出对应源码位置。本节不要求代码修改、功能测试或性能测量。

**阅读深度**：能解释核心入口的调用方、输入、处理、输出与状态变化，推演具体请求的完整执行过程；已掌握的架构和机制快速核对，重点深入尚未吃透的代码。

**结束标准**：能沿 nano-vLLM 讲清请求调度、KV 管理、模型输入与实际执行的连接，并说明已对照部分与真实 vLLM 的差异及源码依据。源码阅读、请求推演与对照复盘即可完成本节，不以代码修改、功能测试或 benchmark 作为结束条件。完成后等待复盘与指令，再进入后续内容。

### 5.5：NCCL、拓扑与通信成本模型

**当前安排**：暂时没有多卡资源，先推进理论学习与手工推演，具体实验统一延后，本机单卡辅助实验也暂不安排。多卡基线与实际时间线分析保留为资源具备后补做的内容。

**5.5.1 通信语义与执行顺序**：

- 理解 communicator、rank 与设备的关系，以及 Broadcast、AllReduce、AllGather、ReduceScatter、AllToAll 的输入输出和使用场景。按“每个 rank 原来有什么数据 → 操作如何组织数据 → 每个 rank 最后得到什么数据”推演数值、shape、分块和顺序，再连接推理中的部分结果求和、分片收集与数据交换。
- 理解 CUDA stream、异步提交、操作完成与数据依赖，能解释后续计算何时可以安全使用通信结果。

**5.5.2 拓扑与通信成本模型**：

- 区分 GPU 显存访问与 GPU 间通信，理解 PCIe、NVLink、共享链路及 rank placement 对数据路径和可用带宽的影响。
- 理解 latency-bound 与 bandwidth-bound，推导 ring AllReduce 的近似每 rank 发送量 `2 × (P - 1) / P × message_size`；明确 `P` 为 rank 数、`message_size` 为每 rank 输入数据的字节数，并区分发送量与发送、接收合计量。
- 建立包含启动延迟和数据传输时间的简化成本模型，解释小消息为什么难以达到峰值带宽；区分操作耗时、algorithm bandwidth 与 bus bandwidth，以及理论下界、换算指标和实际测量的边界。ring 用于模型推导，不据此认定实际 NCCL 必然采用 ring。

**5.5.3 测量方法与性能分析**：
- 理解 GPU P2P、显存带宽和 `nccl-tests` 分别回答什么问题，学习如何控制消息大小、GPU 数量和拓扑，确定计时边界并解读结果；当前使用明确标注来源或假设的示例学习，不启动实验。
- 理解通信与计算重叠、同步等待、straggler 和 rank placement，结合示意时间线分析依赖与空洞，学习将来如何用 Nsight Systems 验证；示例与手工推演不作为真实重叠或性能证据。

**学习方式与深度**：每个小阶段先一次性提供完整 Markdown 讲义，等阅读、提问并明确准备好后再进入后续环节。理论讲义与实验记录分开。重点达到能推演数据变化、计算通信成本、解释指标与性能现象的程度；暂不深入 NCCL 内核实现、多机网络调优或完整分布式训练，也不提前展开 5.6 的完整多卡并行策略。

**当前学习部分的结束标准**：能完成上述通信语义与执行顺序推演，说明成本模型的假设与局限，并解释基线测量方法和常见等待原因。分别记录“理论与推演已完成”和“多卡实践待补”，不以当前完成理论学习代替实测验证。

**资源具备后补做**：先核对实际硬件、拓扑与现有工具，再开展 GPU P2P/显存带宽和 `nccl-tests` 基线，记录 latency、algorithm bandwidth、bus bandwidth，并结合 Nsight Systems 分析实际通信与计算的重叠和等待；完成基线后再开展多卡模型扩展实验。保留环境、命令、配置、原始结果和结论边界，不用单 GPU、多进程或 CPU 模拟替代跨 GPU 性能证据。

### 5.6：多卡并行策略

**当前安排**：先完成双卡 TP 的理论推演，到一个完整 FFN 算例为止。DP、PP 留作后续主线，CP/DCP 和 EP 按模型与负载需求展开。

1. **TP（当前先学）**。以一个 dense FFN 为例，对照 TP=1 和 TP=2，沿 column parallel linear、逐元素激活、row parallel linear 画出每个 rank 的权重和中间张量。说明为什么两层之间可以保留分片，以及在各 rank 都需要完整输出时，为什么要对部分结果做 SUM AllReduce。
   - 给定输入 token 数、hidden size、中间维度和 dtype，算出每卡的 FFN 权重字节数、每次 collective 的每 rank 输入字节数与每次 FFN 前向的调用次数。用 5.5 的模型估算通信时间，解释计算分摊后整层延迟还取决于哪些开销。实际发送量按通信算法另算，整模型显存另计 KV Cache 和临时缓冲区。
   - 后续再对比输出需要拼接或继续分片时的 AllGather、ReduceScatter，推导通信位置、消息大小和调用频率。
2. **DP（后续主线）**。用两个 dense 模型副本分流请求的例子，算出每个副本的权重显存和全部副本的总权重占用，解释请求分配怎样影响总吞吐和排队。区分外部负载均衡、多进程 engine 和框架内 DP scheduling。
3. **PP（后续主线）**。用两段流水线画出各段的层、激活传输和等待，计算一次段间传输的字节数，解释较慢的 stage 怎样限制吞吐，以及 microbatch 怎样影响流水线空闲时间。按推理负载分析 Prefill 和 Decode 的执行节奏。
4. **并行策略比较（TP、DP、PP 学完后）**。对同一模型、GPU 配置和请求负载，先估算每卡权重、KV Cache 和通信，再比较模型能否装下、单请求延迟与总吞吐的取舍。给出一种配置选择，并写清所依赖的负载和拓扑条件。
5. **CP/DCP、EP（按需展开）**。先理解各自切分什么。遇到长上下文或 KV Cache 扩展问题，再深入 CP/DCP 的 KV 分片与 Attention 通信。进入 MoE 场景后，再分析 EP 的 token dispatch/combine、AllToAll、专家负载不均衡和 capacity。

**当前理论完成标准**：能独立画出双卡 FFN 的数据流，从张量形状推导通信位置、消息大小和次数，算出每卡权重占用，并解释通信成本如何影响整层耗时。输出一份算例推演，完成后复盘并暂停。

**资源具备后验证**：先补 5.5 的 GPU P2P 与 NCCL 基线，再用同一个模型、精度和请求负载对比 TP=1/2，记录延迟、吞吐与每卡峰值显存，结合基线解释实测与估算的差异。TP 对照完成后，再按检查点 D 选一种 DP 或 PP 配置做扩展对照。

### 5.7：高级推理优化（完成主线后再展开）

1. **CUDA Graph**：理解减少 CPU launch overhead 的收益、静态 shape/buffer 约束和额外显存成本。
2. **量化**：区分 weight-only、W8A8/FP8 与 KV Cache quantization；同时验证精度、显存、带宽、kernel 支持和真实吞吐，不能只看模型文件大小。
3. **Speculative Decoding**：理解 draft/verify、acceptance rate、额外计算与降低串行 decode step 数之间的权衡。
4. **Kernel backend 选择**：对 Attention、GEMM/MoE 后端做 shape-aware 对比，把阶段三、四的 kernel 性能模型带回系统分析。

### 5.8：SGLang 与 PD 分离（综合拓展）

1. 先通过 SGLang 理解 RadixAttention、prefix-aware/cache-aware scheduling，并用共享前缀 workload 与 vLLM 做同协议比较。
2. 再理解 PD 分离：为什么 Prefill 与 Decode 资源特征不同，统一调度为何互相干扰，以及 KV 从 Prefill 节点传输到 Decode 节点的代价。
3. 分析 KV transport、网络带宽、路由、负载均衡、backpressure 和故障恢复。PD 分离不是免费加速，应比较统一部署与分离部署在给定 SLO 下的 goodput。
4. 没有至少双 GPU 时，完成架构/通信量推导和源码链路即可；不要在单卡上伪造“多卡优化结论”。

## 阶段六：深度学习编译器与异构加速器后端
**目标**：把阶段二的编译器架构能力、阶段三的算子性能模型和阶段四的 lowering / 指令映射能力，连接到实验室的 FPGA 深度学习加速器全流程项目中。最终要能理解并参与“模型图 -> IR -> 图优化 -> 算子调度 -> 内存规划 -> 后端代码生成 / Runtime -> FPGA 加速器执行”的完整链路。

**预计时间**：长期主线，研 0 到研一持续推进

**核心知识点**：
1. **深度学习编译器主链路**：
   - 理解前端输入：PyTorch、ONNX、自研模型描述如何进入编译器。
   - 理解中间表示：计算图 IR、算子 IR、Tensor shape / dtype / layout / device metadata。
   - 理解优化 Pass：常量折叠、死代码消除、公共子表达式消除、算子融合、layout transform、内存复用。
   - 理解 Lowering：高层算子如何逐步变成硬件后端能执行的低层指令、调度描述或 kernel 调用。
2. **Runtime 与调度系统**：
   - 理解模型执行时不是“直接跑 Python”，而是 Runtime 按计算图调度算子、管理内存、同步设备。
   - 学会看懂 device dispatch、operator registry、kernel launch、stream / event、host-device memory copy。
   - 对照你阶段二写过的 Factory Registry，把它升级成真实框架中的算子注册与后端选择机制。
3. **FPGA 加速器后端认知**：
   - 把 GPU 的 SM / Warp / Global Memory / SRAM 思维映射到 FPGA 的 PE array、DSP、BRAM/URAM、AXI 带宽、pipeline、dataflow。
   - 理解 FPGA 上的关键问题：片上存储容量有限、数据搬运贵、pipeline 是否打满、算子是否适合流式化。
   - 学会从算子角度分析：卷积、GEMM、LayerNorm、Softmax、Attention 在 FPGA 上分别受什么资源限制。
4. **算子到硬件的映射能力**：
   - 学会描述一个算子的计算量、访存量、数据复用模式和中间张量生命周期。
   - 对同一个算子同时思考 GPU/Triton 实现和 FPGA 实现：哪些优化思想相同，哪些受硬件约束不同。
   - 重点关注 GEMM/Conv/Attention/LayerNorm/Softmax，因为它们是深度学习加速器最常见的核心算子。
5. **工程落地能力**：
   - 能读懂实验室已有编译器和加速器项目的模块边界：frontend、IR、pass、scheduler、codegen、runtime、driver。
   - 能为一个新算子补全：语义定义、shape inference、图优化规则、后端 lowering、测试样例、性能 benchmark。
   - 能写出工程文档：算子输入输出、支持 dtype/layout、硬件资源估算、性能对比、已知限制。

**建议实战任务**：
1. **任务一：读实验室加速器项目链路**
