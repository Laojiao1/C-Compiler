## 阶段一：C++ 核心工程
**目标**：摆脱 Python 的思维定势，跨越 C++ 的内存管理大关，并具备工业级的高并发编程能力。不要浮于表面，必须亲自动手“造轮子”。

**预计时间**：2 - 3 周

**核心知识点**：

1. **现代内存模型与 RAII**：搞懂左值/右值引用、`std::move`。彻底理解 RAII（资源获取即初始化）机制，这是 C++ 不依赖垃圾回收（GC）也能安全管理内存的核心哲学。
2. **手写智能指针 (硬核必做)**：不要只学理论！自己定义类实现简易版的 `std::unique_ptr` 和 `std::shared_ptr`。
   - *难点*：
   - 彻底搞懂引用计数（Reference Counting）在哪里增加和减少
   - 如何重载 `*` 和 `->` 运算符
   - 如何正确处理拷贝构造函数与移动赋值函数。
3. **高并发编程与线程池 (硬核必做)**：掌握 `std::thread`, `std::mutex`, `std::condition_variable`。
   - *难点*：在 TVM 或底层算子调度中，线程池是标配。你必须手写一个 Thread Pool，理解“任务队列”和“生产者-消费者”模型，搞懂如何通过条件变量唤醒空闲线程。
4. **LRU Cache (数据结构大考)**：结合哈希表 `std::unordered_map`（负责 O(1) 查找）和双向链表 `std::list`（负责 O(1) 插入和删除），自己造一个高频面试考点 LRU 缓存。

**推荐教程/资源**：
*   **视频（强烈推荐）**：B站搜索 **“侯捷 C++ 面向对象高级编程”（上下两部）**。讲透内存模型和面向对象。
*   **代码参考（线程池）**：Github 搜索 `progschj/ThreadPool`。这是一个不到 100 行的经典 C++11 线程池，逐行抄一遍并理解。
*   **实战靶场（LRU）**：LeetCode 第 146 题 (LRU 缓存)，强制自己只用 C++ 提交直到击败 90% 以上用户。
*   **书籍（当字典查）**：《Effective Modern C++》（重点看智能指针和右值引用的条款）。

## 阶段二：编译器级 OOP 与跨语言桥梁
**目标**：掌握 AI 框架（如 PyTorch、TVM）底层的代码架构模式，彻底打通 C++ 与 Python 的生态壁垒，让你的 C++ 算子能在 PyTorch 中跑起来。

**预计时间**：2 周

**核心知识点**：
1. **高频设计模式 (重点关注 Visitor)**：
   - **访问者模式 (Visitor Pattern)**：AI 编译器核心中的核心。无论你是在 TVM 里遍历 TensorIR，还是在 PyTorch 里遍历 `torch.fx` 的抽象语法树，全都靠 Visitor。
   - **工厂模式 (Factory Pattern)**：用于底层算子库的动态注册机制（比如根据不同硬件动态调起不同的算子）。
2. **泛型编程 (Templates)**：掌握类模板与函数模板。不需要学深奥的元编程，但必须能看懂。因为优秀的算子代码（比如 Triton 的 C++ 后端）通常是模板化的，为了用同一套代码兼容 FP32/FP16/INT8 等不同数据类型。
3. **PyBind11 跨语言通信 (极其重要！)**：这是你从纯 C++ 工程师跨越到 AI Infra 工程师的唯一桥梁。你需要知道如何将 C++ 变量/矩阵转换为 Python 的 Numpy/Tensor 对象。
4. **编译器 IR / Pass 基础 (衔接后续加速器编译栈)**：
   - 从普通 AST 进一步升级到计算图 / IR 思维，理解 Node、Edge、DAG、Tensor metadata。
   - 学会写最小版 Pass Manager，并实现 Constant Folding、Dead Code Elimination、Operator Fusion、Shape / dtype / device inference。
   - 理解 Pattern Rewrite：不要只会遍历 IR，还要能识别模式并替换子图，这是后续做算子融合、图优化、硬件后端 lowering 的基础。

**推荐教程/资源**：
*   **图文网站（设计模式）**：[Refactoring.guru - 访问者模式](https://refactoringguru.cn/design-patterns/visitor)（图解非常棒，生动易懂）。
*   **视频（泛型编程）**：B站搜索 **“侯捷 C++ STL 体系结构与内核分析”**，顺带就能把泛型和模板领悟了。
*   **官方文档（必看）**：[PyBind11 官方文档 - First Steps](https://pybind11.readthedocs.io/en/stable/basics.html)。写一个极简的 C++ 加法函数，用它打包给 Python 调用。
*   **开源代码库**：Github 搜索 `pytorch/extension-cpp`，学习 PyTorch 官方推荐的 C++ 自定义算子扩展写法。
*   **编译器补充（进阶）**：阅读 TVM / MLIR / PyTorch FX 的 IR 与 Pass 相关资料。此阶段不要求啃完整源码，但必须能理解“图 -> IR -> Pass -> Lowering -> Runtime”的主链路。

**当前完成状态（已达标，可进入阶段三）**：
1. **TVM 入门已完成**：
   - 已粗略了解 TVM 架构，以及两层 IR：Relay IR、TensorIR。
   - 已通过 Docker 搭建 TVM 环境。
   - 已用 TVM Schedule 对 GEMM 做过简单优化，包括内存重排、分块计算、累加优化，让矩阵乘法跑得更快。
   - 已将训练好的模型导出为 ONNX，并通过 TVM 现有工具完成简单编译优化和运行。
2. **阶段二判断**：
   - 当前 TVM 掌握程度属于“概念 + 入门实战级”，已经足够支撑进入阶段三。
   - 暂时不需要停下来深入 TVM 源码、MLIR 或完整 Pass 框架。
   - 后续在阶段六系统回补编译器基础、TVM TensorIR、Schedule 和 Relax；阶段七进入 MLIR，阶段八再完成外部算子与后端接入，不为“学完某个框架”一次性啃完全部源码。

## 阶段三：算子性能模型与 Triton/GPU 实战
**目标**：在扎实的 C++ 系统架构底盘上，建立可迁移的算子性能模型。GPU/Triton 是训练场，核心不是只会写 Triton 语法，而是理解 Tiling、访存复用、带宽瓶颈、并行划分和 Benchmark 证据；这些能力后续可以迁移到实验室 FPGA 深度学习加速器和其他异构后端。

**预计时间**：4 - 6 周

**阶段三执行原则**：
阶段三的六大知识点不是线性前置条件，不需要全部学完再写代码。它们是围绕六个算子项目逐步展开的知识地图。

正确顺序是：
```text
01_vector_add
  只需要先学 Triton 最小语法、block、mask、load/store、GB/s

02_softmax
  再补 reduction、数值稳定性、片上复用

03_matmul
  再补 tiling、tl.dot、Tensor Core、TFLOPS

04_layernorm
  再补 reduction + elementwise fusion、register pressure

05_attention_naive
  再补 Attention 计算图、中间矩阵代价

06_flash_attention_forward
  最后综合 online softmax、tiled attention、SRAM/register 复用
```

因此当前第一步不是系统学习完所有 GPU 理论，而是先完成 `Triton/01_vector_add/` 的正确性、benchmark 和笔记闭环。

**核心知识点**：
1. **GPU 性能模型 (先知道瓶颈在哪里)**：
   - 彻底搞懂核心概念：**SM (流式多处理器)**、**Warp (线程束)**、Occupancy、Register Pressure。
   - 深刻理解存储层级：**Global Memory (全局显存)**、**L2 Cache**、**Shared Memory/SRAM**、Register。
   - **生死线知识**：彻底搞懂什么是**访存合并 (Coalesced Memory Access)**，以及为什么 stride、alignment、连续内存会直接决定带宽利用率。
   - 建立 Roofline 思维：判断一个算子是 **memory-bound** 还是 **compute-bound**，并用 GB/s、TFLOPS、理论峰值百分比解释性能。
2. **Triton 编程模型 (从线程思维切换到 Blocked Program 思维)**：
   - 掌握 `@triton.jit`、`tl.program_id`、`tl.arange`、`tl.load`、`tl.store`、mask、stride、block size。
   - 理解 Triton 的核心抽象：一个 program instance 负责一个 block，而不是手动管理每个 CUDA thread。
   - 学会阅读生成的性能现象：block 太小会调度开销大，block 太大会寄存器压力高，mask 会影响边界处理但不能乱用。
3. **官方三板斧 (必须手写 + Benchmark)**：
   - `Vector Addition`：理解 block 切分、mask、连续访存、理论带宽。
   - `Fused Softmax`：理解 row-wise reduction、数值稳定性、SRAM/寄存器复用，避免反复读写 global memory。
   - `Matrix Multiplication`：理解 `BLOCK_M/N/K`、tiling、accumulator、`tl.dot`、Tensor Core、不同 shape 下的性能差异。
4. **Benchmark 与性能诊断 (算子优化必须有证据)**：
   - 每个算子至少对比三版：PyTorch baseline、Triton naive、Triton optimized。
   - 每个 benchmark 必须输出：耗时、GB/s 或 TFLOPS、speedup、correctness check (`torch.allclose`)。
   - 学会使用 `triton.testing.do_bench`、`@triton.testing.perf_report`，并记录不同 block size、num_warps、num_stages 的影响。
5. **PyTorch Extension 衔接 (从裸 kernel 到工程算子)**：
   - 从 PyBind11/NumPy 过渡到 `torch::Tensor`，理解 contiguous、stride、dtype、device、storage、lifetime。
   - 跑通一个 PyTorch C++/CUDA custom op，重点不是深挖 CUDA 语法，而是理解 Python -> Dispatcher -> Tensor -> Kernel 的调用链。
   - 为后续算子做 dtype dispatch 和 device dispatch 的工程准备。
6. **大模型算子实战：简化版 FlashAttention**：
   - 先写 naive attention：显式计算 `QK^T`、softmax、再乘 `V`，作为正确性基线。
   - 再写 tiled attention forward：不显式 materialize `QK^T`，理解 online softmax 的 `m_i` / `l_i` 更新。
   - 分阶段支持：固定 shape -> causal mask -> fp16/bf16 -> benchmark 对比 PyTorch SDPA -> 再考虑 backward。

**建议项目结构**：
```text
Triton/
  01_vector_add/
    kernel.py
    test_correctness.py
    benchmark.py
    notes.md
  02_softmax/
  03_matmul/
  04_layernorm/
  05_attention_naive/
  06_flash_attention_forward/
  benchmarks/
  notes/
```

**项目目录与知识点对应关系**：
1. **`01_vector_add/`：Triton 执行模型与基础访存**
   - 对应知识点：`tl.program_id`、block 切分、`tl.arange`、`tl.load` / `tl.store`、mask 边界处理。
   - 性能重点：这是典型 memory-bound 算子，重点计算 GB/s，理解连续访存和访存合并。
   - 学习目的：理解一个 Triton program instance 如何负责一块数据，而不是从 CUDA thread 视角手动管理每个线程。
2. **`02_softmax/`：Reduction、数值稳定性与片上复用**
   - 对应知识点：row-wise reduction、`max` / `sum` 规约、数值稳定 softmax、SRAM / register 复用。
   - 性能重点：避免把中间结果反复写回 global memory，理解 fused softmax 为什么能快。
   - 学习目的：为后续 FlashAttention 的 online softmax 打基础。
3. **`03_matmul/`：Tiling、Tensor Core 与 compute-bound 分析**
   - 对应知识点：`BLOCK_M/N/K`、tiling、accumulator、`tl.dot`、num_warps、num_stages。
   - 性能重点：这是典型 compute-bound 算子，重点计算 TFLOPS，并分析不同 shape / block size 对性能的影响。
   - 学习目的：建立 GEMM 性能模型；后续 Conv、Attention、MLP 都绕不开 MatMul。
4. **`04_layernorm/`：Reduction + Elementwise Fusion**
   - 对应知识点：均值、方差、归一化、elementwise 操作融合、register pressure。
   - 性能重点：尽量用一次读写完成多步操作，理解算子融合为什么能减少 global memory traffic。
   - 学习目的：训练真实模型中高频非 GEMM 算子的优化思路。
5. **`05_attention_naive/`：Attention 正确性基线**
   - 对应知识点：`QK^T`、softmax、`P @ V`、中间张量生命周期。
   - 性能重点：显式 materialize `QK^T` 会造成巨大显存占用和访存压力。
   - 学习目的：作为 FlashAttention 的 correctness baseline，先把 Attention 计算图彻底吃透。
6. **`06_flash_attention_forward/`：阶段三综合项目**
   - 对应知识点：tiled attention、online softmax、`m_i` / `l_i` 更新、SRAM / register 复用、hardware-aware algorithm。
   - 性能重点：不显式生成完整 `QK^T`，通过分块和在线归一化降低显存流量。
   - 学习目的：综合 MatMul、Softmax、Tiling、Benchmark，完成一个真正有含金量的大模型算子。
7. **`benchmarks/`：通用性能工具**
   - 放通用 benchmark 函数、GB/s 计算、TFLOPS 计算、PyTorch baseline 对比、结果表格输出。
   - 每个算子的性能结论都必须来自这里的可复现实验，而不是主观感觉。
8. **`notes/`：性能模型与复盘**
   - 放阶段三总笔记，例如 GPU 性能模型、访存合并、Roofline、Triton 调参、GPU vs FPGA 后端对比。
   - 这里不是可选项。这个方向不能只写代码，必须能解释性能。

**每个算子的完成标准**：
1. 正确性：至少覆盖普通 shape、非 2 的幂 shape、边界 mask、不同 dtype。
2. 性能：必须和 PyTorch baseline 对比，并能解释快在哪里、慢在哪里。
3. 笔记：`notes.md` 里必须写清楚访存量、计算量、瓶颈判断、block size 选择理由。
4. 复盘：每次优化只改一个变量，例如 `BLOCK_SIZE`、`num_warps`、`num_stages`，避免盲调。

**推荐教程/资源**：
*   **视频（GPU架构）**：谭升的 CUDA 教程。**注意**：阶段三暂时不深入 CUDA C++，优先借助 Triton 提高 GPU Kernel 编程的抽象层级并建立算子性能模型；阶段四再系统学习 CUDA，把 Triton 编译器隐式完成的线程组织、访存、同步和 Tensor Core 映射显式写出来。

## 阶段四：Triton 编译映射与 CUDA Attention 深入

**目标**：阶段三解决“会写、会测、会优化 Triton 算子”，阶段四继续回答两个更底层的问题：Triton 编译器如何把 blocked program 映射到 GPU 线程、Warp、共享内存和机器指令；同一个算子改用 CUDA C++ 后，性能策略如何显式落到线程组织、访存、同步和 Tensor Core 上。

**定位**：这是算子开发方向的必修阶段，也是连接“算子优化”和“编译器后端”的关键桥梁。不要在阶段三之前展开，以免同时被 Triton 语法、CUDA 线程模型和编译器 IR 三套抽象拖慢。

**建议执行顺序**：
```text
4.0 补 CUDA 映射最小前置：grid / block / thread / warp、线程索引、存储归属和线程视角的合并访存
4.1 以阶段三已经写熟的 vector_add / softmax / matmul 作为观察样本追踪 Triton 编译链和每一层 IR 的语义变化
4.2 系统学习 CUDA C++ 最小必需集，并重写 vector_add / reduction / softmax
4.3 从 naive GEMM 逐步优化到 tiled GEMM、register blocking 和 Tensor Core
4.4 拆解 Attention：QK^T -> Softmax -> P@V -> fused/tiled attention
4.5 实现并分析简化 CUDA Attention Forward
4.6 用 Nsight Compute 和生成指令解释 Triton 版与 CUDA 版的性能差异
```

`4.0` 只建立阅读 TTGIR 所需的硬件坐标系，并用一个最小 CUDA Vector Add 对照 `blockIdx.x`、`threadIdx.x` 与 Triton Program。此时不展开 CUDA Softmax、GEMM、Attention、复杂共享内存优化或 Tensor Core 编程；这些内容仍放在 Triton lowering 之后。

**核心知识点**：
0. **CUDA 映射最小前置**：

- 理解 `grid -> block/CTA -> warp -> thread` 的执行层次，能读懂 `blockIdx.x`、`threadIdx.x`、`blockDim.x` 和 `gridDim.x`。
- 建立初步对应：一个 Triton Program 通常映射为一个 GPU CTA，但 Triton Program 不等于 CUDA Thread，`BLOCK_SIZE` 也不等于 CUDA 线程数。
- 理解寄存器由线程私有、Shared Memory 由同一 Block/CTA 共享、Global Memory 由整个设备访问。
- 从线程视角理解合并访存：不仅要看逻辑地址连续，还要看同一条访存指令中相邻线程实际访问的地址。
- 只写一个最小 CUDA Vector Add 作为映射参照，不在此处进行复杂 CUDA 优化。

1. **Triton 到 GPU 指令的映射**：
   - 建立主链路：Python DSL / JIT AST -> Triton IR（TTIR）-> TritonGPU IR（TTGIR）-> LLVM IR -> PTX -> cubin / SASS。
   - TTIR 重点看算子语义和张量级数据流；TTGIR 重点看 layout、线程/warp 分配、shared memory、layout conversion；PTX/SASS 重点确认最终 load/store、shuffle、barrier、MMA 等指令是否符合预期。
   - 学会保存并阅读一个小 kernel 的各层 IR，对照 `tl.program_id`、`tl.arange`、`tl.load`、reduction、`tl.dot` 分别被 lowering 成什么。
   - 理解编译器不是机械翻译语法，而是在做 layout propagation、coalescing、shared-memory allocation、instruction selection 和目标架构相关 lowering。
2. **CUDA C++ 最小必需集**：
   - thread / warp / block / grid 映射，global/shared/register memory，barrier，warp shuffle，向量化访存和 bank conflict。
   - 掌握必要的 stream、event、异步拷贝与 kernel launch；暂时不追求把 CUDA API 全部学完。
   - 学会检查资源使用：registers per thread、shared memory per block、occupancy、memory throughput、warp stall reason。
3. **GEMM 优化阶梯**：
   - `naive` -> global-memory coalescing -> shared-memory tiling -> register blocking -> double buffering / software pipeline -> vectorized load -> Tensor Core。
   - Tensor Core 分三层推进：先理解 tile、dtype、layout 和硬件映射要求；再用 WMMA 或较高层接口跑通 correctness 与 benchmark；最后阅读 PTX MMA、CUTLASS / CuTe 的实现思路。
   - 首轮目标是能解释 Tensor Core mapping，不要求直接手写 `ldmatrix`、`mma.sync`、复杂 swizzle 或接近 CUTLASS 水平的极致 GEMM。
   - 每一步只改变一个主要策略，记录适用 shape、资源消耗、TFLOPS 和相对 cuBLAS 的峰值百分比。
   - 目标不是手写超过 cuBLAS，而是能解释库实现为何需要分块层次、流水和数据布局。
4. **Softmax 优化阶梯**：
   - `naive multi-kernel` -> row-wise 单 block -> warp shuffle reduction -> shared-memory reduction -> fused scale/mask/softmax。
   - 正确处理减最大值、FP32 accumulation、非 2 的幂长度、长序列跨 block 情况。
   - 对比不同序列长度下带宽、launch 次数、同步开销和 occupancy 的变化。
5. **CUDA Attention 综合实战**：
   - 在 05_cuda_attention/ 中实现 Unfused Attention 基线与 Tiled Online FlashAttention Forward，对比二者的正确性、Kernel 时间、启动次数及中间矩阵 S/P 的全局内存读写代价。
   - 重点在于把已经完成的 GEMM、融合 Softmax 与 Online Softmax 组合为完整 Attention 数据流。

**资源具备后验证**：先补 5.5 的 GPU P2P 与 NCCL 基线，再用同一个模型、精度和请求负载对比 TP=1/2，记录延迟、吞吐与每卡峰值显存，结合基线解释实测与估算的差异。TP 对照完成后，再按检查点 D 选一种 DP 或 PP 配置做扩展对照。

### 5.7：高级推理优化（完成主线后再展开）

1. **CUDA Graph**：理解减少 CPU launch overhead 的收益、静态 shape/buffer 约束和额外显存成本。
2. **量化**：区分 weight-only、W8A8/FP8 与 KV Cache quantization；同时验证精度、显存、带宽、kernel 支持和真实吞吐，不能只看模型文件大小。
3. **Speculative Decoding**：理解 draft/verify、acceptance rate、额外计算与降低串行 decode step 数之间的权衡。
4. **Kernel backend 选择**：对 Attention、GEMM/MoE 后端做 shape-aware 对比，把阶段三、四的 kernel 性能模型带回系统分析。

### 5.8：SGLang 与 PD 分离（综合拓展）

1. 先通过 SGLang 理解 RadixAttention、prefix-aware/cache-aware scheduling，并用共享前缀 workload 与 vLLM 做同协议比较。
2. 再理解 PD 分离：为什么 Prefill 与 Decode 资源特征不同，统一调度为何互相干扰，以及 KV 从 Prefill 节点传输到 Decode 节点的代价。
3. 分析 KV transport、网络带宽、路由、负载均衡、backpressure 和故障恢复。PD 分离不是免费加速，应比较统一部署与分离部署在给定 SLO 下的 goodput。
4. 没有至少双 GPU 时，完成架构/通信量推导和源码链路即可；不要在单卡上伪造“多卡优化结论”。

**建议实战检查点**：
1. **检查点 A（GPT-2 单卡基础）**：手写 GPT-2 与参考权重/logits 对齐，完成三条 Decode 路径、KV Cache 显存账本和 profiler 报告，能解释 Prefill/Decode shape 与瓶颈。
2. **检查点 B（服务基础）**：保留已有离线吞吐参考，完成一次真实在线生成调用，能解释关键性能指标、请求排队及计时与 Token 计数边界；不要求手写压测工具或完成系统扫描。
3. **检查点 C（源码能力）**：沿 nano-vLLM 解释一次调度到模型执行及结果反馈的过程，说明与真实 vLLM 已对照的关键差异并指出源码依据；不要求提交代码修改、测试或 benchmark 结果。
4. **检查点 D（多卡能力，待资源具备后完成）**。先补 5.5 的拓扑与 NCCL 基线，再按 5.6 的统一条件对比 TP=1/2，随后验证至少一种 DP 或 PP 配置并解释扩展效率。当前单独记录双卡 FFN 理论推演进度，多卡实测标为待补。
5. **检查点 E（综合拓展）**：量化、speculative decoding、SGLang/PD 中至少选择一个做完整控制变量实验。PD 不再作为所有硬件条件下的强制要求。

**原有无多卡环境替代任务（保留参考，暂停期间不执行）**：
恢复阶段五时，再按项目需要选择通信语义、成本模型、测量方法或纸面推演；当前不以继续补理论替代多卡实践。以下为原有可选任务。

1. 用矩阵维度推导 TP 中每层 collective 的类型、次数、消息量，并估算在 PCIe/NVLink 给定带宽下的通信下界。
2. 阅读 vLLM distributed executor 与 parallel linear 实现，画 rank/group 与算子切分图。
3. 使用单卡完成 DP/PP/PD 的调度模拟和容量规划，但明确标记为模型推导，不声称获得真实扩展性能。
4. 真正的多卡 benchmark 延后到实验室服务器，不阻塞阶段五其他检查点。

**阶段五完成标准**：
1. 能从已验证的 GPT-2 单卡实现出发，解释 Transformer 层、Prefill/Decode shape、KV Cache 生命周期、显存账本和主要瓶颈，并能说明现代模型结构会带来哪些变化。

5. 面对给定模型、GPU 数量、显存、互联和 SLO，能给出并行、缓存、调度与高级优化方案及其代价。
6. 最终形成一份可复现实验报告，包含环境、命令、workload、原始结果、图表、失败实验和结论边界。

## 阶段六：编译器基础与 TVM 实践

**目标**：从“会写算子、会阅读 IR”，进入“能表达计算、实现变换、解释生成代码”的阶段。通过 TVM 把已有的 tiling、访存和融合经验变成编译器中的具体操作。

**起点判断**：已有 C++ Visitor/Mutator、Factory Registry、PyBind11、CUDA/Triton 和 IR 阅读基础；TVM 已做过 Schedule 优化 GEMM、ONNX 模型编译运行。接下来重点补齐 IR 的语义约束、Pass 开发、调度合法性、图与算子之间的 Lowering、Runtime 边界。原路线中列出的 Pass Manager、完整 shape inference 等目标，不直接视为已经掌握。

### 6.0：环境基线与贯穿案例

先核对旧 TVM Docker 的版本、镜像与示例，记录可运行的入口。新实践使用独立环境，固定 TVM release / commit、对应文档和构建配置；MLIR 到阶段七再单独准备。当前无需安装两套完整工具链。

**第一个可运行目标**：用现成环境或可获得的预构建版本，编译并执行一个极小的计算（如 Add），保存一份 IR 和执行结果；再修改一个操作或输入 shape，确认结果符合预期。先用这个真实编译链作为后续讲解的坐标系。环境准备原则上控制在一次学习任务内；若遇到兼容性问题，先定位具体障碍、选择可用版本或 CPU 路径，不把反复构建、换版本、配置工具链当作编译器学习进度。

**版本选择原则**：TVM 当前官方主线教程以 Relax 表达模型图、TensorIR 表达张量程序；旧 Relay 教程用于理解旧项目，不作为新路线默认入口。当前在线文档还出现了 TensorIR 的 `tirx` / `s_tir` 模块拆分，具体名称和接口以选定版本为准，不能把旧 `tvm.tir` 示例与新接口直接拼接。参考 [TVM Quick Start](https://tvm.apache.org/docs/get_started/tutorials/quick_start.html) 与 [TensorIR 文档](https://tvm.apache.org/docs/deep_dive/tensor_ir/index.html)，进入实验时选定支持所需功能且能在本机跑通的版本。

当前 Windows 侧确认有单张 RTX 5060 Laptop GPU、约 8GB 显存。旧环境信息可参考 [WSL2 开发环境清单](./WSL2开发环境清单.md)，但 TVM、LLVM、CUDA target 和 MLIR 工具可用性须在开始相应实验时重新核对。CPU 路径先跑通，再验证单 GPU；不预设旧 Docker 已支持当前 GPU。

**贯穿三个阶段的主案例**：

```text
X[M,K] @ W1[K,N] -> Add(b1[N]) -> ReLU
    -> @ W2[N,P] -> Add(b2[P]) -> Y[M,P]

首次运行：M=32, K=128, N=256, P=64，FP32、连续布局
边界验证：M=37, K=131, N=259, P=67
```

先取其中的 `MatMul + Bias + ReLU` 子图学习，再扩展为完整两层 MLP。参数随机生成，与 NumPy/PyTorch 参考结果对齐，不依赖模型下载或训练。性能实验另选少量能暴露瓶颈的 shape，不能用小尺寸教学案例概括大规模性能。

### 6.1：补齐编译器最小基础——IR、分析、Pass 与语义

**要回答的问题**：编译器怎样知道一段变换保持了程序的含义？Visitor 为什么还不足以构成优化器？

**知识范围**：

1. 从 AST、表达式 DAG 到 SSA：区分 Operation 和 Value，理解定义—使用关系、类型、shape、属性与返回值。先用单个基本块学习 SSA；CFG、支配关系和块参数在阶段七遇到控制流时展开。
2. 区分分析与变换：shape/dtype 推导、use-def 分析提供依据，Pass 按条件改写 IR；理解 Pass 顺序、前后条件及改写后需重新检查的信息。
3. 建立合法性意识：广播、dtype、浮点误差、共享子表达式和有副作用的操作都会限制变换。删除无使用者的纯计算与删除内存写入不是同一个判断。
4. 区分图优化、循环调度、Lowering 和代码生成：它们分别改变什么、保留什么语义、引入哪些硬件细节。

**动手任务**：先在 6.0 已经跑通的 TVM 实际 IR 中，构造一个带常量和共享值的短计算图，观察一次现成 Pass 的前后变化；独立预测哪些操作应当被替换或保留，再核对真实 IR 和结果。复习 `2_OOP` 中已有 Visitor/Mutator 实现即可，不要求重新设计 IR 类体系。

必要时才补一个单基本块的极小练习，用真实常量节点、shape/dtype 和 use-def 信息实现一次常量折叠或死代码消除，二选一即可；旧示例中的 `x + 0 -> x` 属于代数简化，不能代替两个常量求值的 Constant Folding。浮点规则先明确适用条件。此练习最多占一个小节，不写自制 Pass Manager、解释器、通用解析器或完整编译器框架；完整的自定义 Pass 放到 6.3 的实际 TVM 中实现。

**验收**：给出一次输入 IR、分析结果、优化后 IR 和执行结果；为错误 shape、共享节点、有用/无用分支准备反例。能解释为什么可改写，以及在哪种输入或语义下不能改写。已能独立完成的部分快速核对，不重复造轮子。

### 6.2：TensorIR 与 Schedule——把 CUDA 优化经验变成编译变换

**要回答的问题**：同一个 GEMM，计算语义不变，编译器怎样改变循环、数据位置与线程分工？

**学习顺序**：

1. 手写最小 TensorIR：从 Add 进入 GEMM，理解函数、Buffer、循环、计算 Block、空间轴、归约轴和初始化。区分 TensorIR 的计算 Block 与 CUDA thread block。
2. 对照已有 CUDA GEMM，逐步练习 `split`、`reorder`、`fuse`、线程绑定；每次保存变换前后 IR，指出元素索引和工作分配怎样变化。
3. 学习缓存读写、`compute_at` / `reverse_compute_at`、shared/local 存储与归约分解；分析生产者/消费者关系、数据依赖、同步与生命周期怎样限制变换。
4. 从生成代码和 profiler 检查访存、线程组织、资源占用；能将一个不合法的调度错误还原为具体依赖问题。
5. 手工调度得到稳定基线后，若遇到 shape 变化导致固定调度失效的问题，再选做一次小预算的规则调度或自动调优实验，理解调度空间、测量、记录与复用。DLight/MetaSchedule 不作为本节必修，不进行大范围盲搜。

**动手任务**：完成 GEMM 的可运行基线、一个 tiling 版本和一个增加数据复用的版本；FP32 先行，FP16/Tensor Core 作为后续加深项。重点学习编译器如何表达既有优化，不再重走整套 CUDA GEMM 优化课程。针对其中一次真实调度，至少追踪一个关键 primitive 或 lowering pass 的实现与前置条件：它如何检查依赖、修改 IR，什么情况下会拒绝变换。停止于能独立预测并验证该行为，不以背熟所有 Schedule API 为目标。

先记录基线，再选定预计可减少的访存或改善的并行瓶颈；若 GPU 目标一时无法运行，先在 CPU 验证循环变换和数值，明确 GPU 实验尚未完成。不要为了补齐 GPU 知识而只阅读大量不可执行的 CUDA lowering 理论，也不要求在 CPU 重复所有 GPU 优化。

**验收**：对普通及尾块 shape 检查正确性；用 IR 和生成代码解释至少两项调度决策；对比未调度/基础调度、手工调度和库基线的适用结果。能说明慢在哪，也算有效结论；不以超过 cuBLAS 为通过条件。

### 6.3：Relax、图优化与自定义 Pass

**要回答的问题**：模型图怎样连接到 TensorIR？为什么把图上的几个节点合成一组，还不能直接证明实际 kernel 已融合？

**知识范围**：Relax 的函数、绑定、数据流与结构信息；图级算子到张量函数的合法化/Lowering；模式匹配、子图边界、Pass pipeline；图融合与循环/内核融合的区别。

**动手顺序**：

1. 直接用 Relax 构建 6.0 的 MLP，跑通 CPU 参考路径，再接单 GPU；保存模型图、张量函数、生成代码和运行结果。
2. 手写一个有明确语义条件的图改写，例如消去连续两次互逆的 transpose；验证中间值有其他使用者时仍需保留哪些节点，并覆盖非互逆排列、错误 shape 等不能直接消去的情况。
3. 分解观察 `MatMul -> Bias -> ReLU` 的变换过程：先确定匹配范围，再检查张量函数与最终 kernel，核对中间 Buffer 和启动次数。具体融合方式使用固定版本提供的机制，不能假设默认 Pass 会把所有算子融合成一个 kernel。
4. 改变一项 Pass 顺序或关闭一项变换，用 IR 差异解释为什么后续匹配、Lowering 或执行发生变化。

图改写示例以验证共享使用者、shape 和合法性为主；若互逆 transpose 已不足以带来新知识，可以换为来自实际计算图的冗余转换或融合子图匹配。完成一个有明确动机的自定义 Pass 即可，不逐个手写所有经典优化，也不要求每个语义简化都产生可测的加速。如果只看到图结构变化，先提出依据并检查最终执行，不能把采用了某个 Pass 当成性能结论。

**验收**：一个自己实现的 Pass，加上一组正例和反例；能追踪主案例从 Relax 到 TensorIR 的一次完整变化；融合结论有生成代码或运行时间线支持，不能只看图中节点数量。

### 6.4：Runtime、内存与部署边界

**要回答的问题**：编译结束后留下什么？谁负责分配内存、传参、启动算子并返回结果？

**动手任务**：

1. 把前面的模型编译产物导出，在新进程中加载并运行，区分编译期、加载期、首次执行与稳定执行。
2. 追踪一个张量从输入进入算子、产生中间值、返回结果的过程；理解 shape/stride/dtype/device、Buffer 生命周期、host-device copy 与同步边界。
3. 估算主案例中间张量的容量，并检查生成程序中的分配、复用或拷贝；内存复用先理解和观察，不要求本节手写通用内存规划器。
4. 选一个关键 Pass，从 Python 入口追踪到实现及测试位置，记录输入、输出、前置条件与核心改写。源码阅读围绕已经做过的实验展开。
5. 做一次最小外部算子调用，优先选已有 CPU/CUDA 实现中接口最简单的一个；确认编译产物可以传参、运行并对齐参考结果。先完成单算子调用，不提前研究整套 BYOC、子图划分或完整后端工程。若 GPU 接入暂受版本限制，保留阻塞记录，CPU 调用先验证 ABI 与传参语义。

**阶段六完成标准**：主案例能实际编译运行；至少完成一个自定义图 Pass、一组有明确问题的 TensorIR 调度实验、一次最小外部函数调用；能解释图、张量程序、生成代码与 Runtime 之间的边界，并保存可重现的环境与结果。到达这里即可进入阶段七；TVM 的其他 API、自动调优、分布式和完整 BYOC 不构成前置条件。

**主要资料**：[TVM Quick Start](https://tvm.apache.org/docs/get_started/tutorials/quick_start.html)、[TensorIR](https://tvm.apache.org/docs/deep_dive/tensor_ir/index.html) 以及同版本文档中的 Relax、Transformation、Pass Infrastructure 和 Runtime 章节。每节只阅读与当前实验对应的内容，配套源码和测试来自相同 commit。

## 阶段七：MLIR 与编译变换开发

**目标**：把阶段六积累的具体经验迁移到可扩展的编译器基础设施，能够用 C++ 开发 Pass、定义小型 Dialect，并把高层张量操作逐步 Lowering 成可执行代码。

**为什么放在 TVM 后面**：先用熟悉的 GEMM 理解调度与图变换，再学习 MLIR 怎样组织这些能力，降低同时面对新框架、新 IR 和新算子的负担。TVM 和 MLIR 是两条编译实践路径；本路线不要求先把 TVM IR 转为 MLIR，也不把二者当作固定串联的上下游。

### 7.0：准备可开发的 MLIR 环境

固定 LLVM/MLIR release 或 commit，文档、头文件、库和工具保持一致。优先使用能够满足当前实验的现成工具，先准备 CPU 所需的工具和测试；进入 7.2 时再配置可独立编译的 C++ 项目。需要源码构建时仅构建所需目标并限制并行度，结合实际内存与磁盘选择配置。GPU 后端到相应实验再启用。

**验收**：能运行 `mlir-opt` 和一个 CPU 执行例子，即进入 7.1；自定义优化工具的构建与运行放在 7.2。构建环境是准备工作，不将“编译成功”当作已经掌握 MLIR。

### 7.1：读写 MLIR，并先完成 CPU Lowering

**知识范围**：Operation、Value、Type、Attribute、Region、Block、Dialect、Symbol；理解 SSA 的定义—使用关系和作用域，在循环与分支中学习块参数与支配关系。

**学习顺序**：

1. 从 `func`、`arith`、`tensor`、`linalg` 的小例子进入，先写 Add 并使用工具验证，再观察已有 GEMM IR；理解 `linalg` 的迭代空间、索引映射、并行轴/归约轴和 destination-passing style。只在新语义确实需要时添加代码，不重复阶段六的完整 GEMM 实现。
2. 学习 `scf`、`memref`，比较张量值与可读写存储的区别；通过 Bufferization 观察何时可以原地写入、何时因读写冲突需要拷贝。
3. 用选定版本支持的 Pass 完成一条 CPU 路径，保存关键层 IR，运行并对齐结果：

```text
linalg / tensor / arith / func
    -> Bufferization，得到基于 memref 的计算
    -> 循环与显式访存（scf / memref / arith 等）
    -> 控制流及 LLVM Dialect
    -> LLVM IR -> CPU 执行
```

这是一条教学路径示意。张量级 tiling/fusion 通常在 Bufferization 前进行；具体 Pass 顺序、内存释放和运行接口按所选版本补齐，不把示意图直接当成可执行命令。

**验收**：从一个 GEMM 解释每层新增的循环、内存和执行细节；能够区分 LLVM Dialect 与 LLVM IR；结果与参考一致。先用 CPU 把编译语义学清，再引入 GPU 线程和存储映射。

### 7.2：用 C++ 开发 Pass 与 Pattern Rewrite

**知识范围**：Pass 注册与嵌套、遍历、Analysis、`PatternRewriter`、匹配与替换、canonicalization、CSE、改写驱动与终止；了解 side effects 对删除、移动和复用操作的限制。

**动手任务**：

1. 实现一个只分析并报告的 Pass，例如统计 GEMM 的 shape、运算量和使用者；先熟悉 IR 对象与遍历边界。
2. 实现一个改写 Pass。可将阶段六已有的合法改写作为短入门练习；若该练习已经熟练，直接选择一个能体现 MLIR 特有约束的实际 IR 改写，例如带 Region 或不同 use-def 条件的变换。使用框架提供的 rewrite 接口维护使用关系，不为比较两套 API 而重复大量等价实现。
3. 使用 `lit` / `FileCheck` 验证 IR 的关键变化，用数值执行验证语义；覆盖匹配成功、条件不满足和改写后仍被使用的值。
4. 对一个小型错误示例练习打印 Pass 前后 IR、检查 verifier、缩小复现输入。避免改写循环和一次遍历中随意删除仍在使用的操作。

**验收**：能够独立实现、注册并运行一个带正反例的 C++ Pass；解释它为何合法、何时触发、何时停止，以及为什么需要这种 Pass 顺序。

### 7.3：自定义 Dialect、Operation 与 Dialect Conversion

**要回答的问题**：现成 Dialect 无法直接表达所需语义时，怎样定义操作，并接入已有优化和代码生成？

**动手任务**：选择一个可在现有 Dialect 中展开、但能体现自定义语义的最小操作。优先选择 `mini.bias_relu` 之类的融合子操作；需要表达完整 `MatMul + Bias + ReLU` 时再扩大。先限制静态 shape、FP32、输入 rank、布局与广播规则。定义它的目的是练习语义约束和转换，不是通过增加一种 Op 声称编译器更快；不搭建完整私有 Dialect 生态，不实现无需求的 parser、printer 或通用动态形状系统。

1. 用 ODS/TableGen 定义操作，补 builder、类型/shape 检查、verifier 和正确的副作用描述；能解析、打印，并拒绝非法输入。
2. 区分“操作合法”与“操作已能执行”：只有定义，没有 Lowering，并不会自动产生机器代码。
3. 编写到 `linalg` / `arith` / `tensor` 等现成操作的转换，复用 7.1 的 CPU 路径运行；理解 `ConversionTarget`、合法/非法操作、Conversion Pattern 和必要时的 `TypeConverter`。
4. 有选择地阅读 Toy 教程第 2～6 章，对照操作定义、改写、接口与逐层 Lowering；无需先从头实现 Toy 的词法/语法解析，也不要求照抄全部章节。

**验收**：一份自定义操作的语义约定、非法输入诊断、转换前后 IR 和可执行结果；转换目标要求消除该操作时，遗漏 Lowering 必须明确失败。自定义融合操作降低为多个普通操作，也不能据此声称已经完成 kernel 融合。

### 7.4：调度、Bufferization 与硬件映射

**要回答的问题**：MLIR 怎样表达已经学过的分块、融合、向量化与线程映射？什么是通用变换，什么必须依赖目标硬件？

**推进顺序**：

1. 在 `linalg` 上完成一次能回答具体问题的 tiling 或 producer-consumer fusion，利用 Transform Dialect 或 C++ 变换接口控制过程；不重新实现所有循环变换算法。
2. 观察优化后的迭代空间，再进行 Bufferization，检查分配、别名、读写冲突与额外 copy；理解它与完整内存规划不是同一件事。以一个实际出现的中间 Buffer 或 copy 为切入点。
3. 从 CPU 向量化和 GPU 线程映射中选择一条实际可运行的路径作为必做实验：优先选择与当前算子研究相关且工具链支持的 GPU 路径，学习线程分工、地址空间、同步、NVVM/NVPTX 与生成 PTX；若 GPU 后端受阻，则用 `vector` 和 CPU 生成代码验证向量化。另一条路径不阻塞本阶段。
4. 将生成代码与已有 CUDA/Triton 实现对照，解释同一个计算为何产生不同的访存、同步或向量化。可将案例换成 Bias-ReLU 或短归约（如 Softmax 的一部分），以覆盖 GEMM 之外的优化约束；无需首轮实现异步流水、最优 Tensor Core GEMM 或学习整套 Affine/多面体理论。

**验收**：完成一次可执行的调度及硬件映射实验，明确目标设备；GPU 工具链若暂不支持所需路径，明确记录阻塞点，GPU 项留作后续项目验证。性能改善用实测确认，未改善时保留 IR、代码与原因分析。CPU 结果不能当作 GPU 性能证据。

**阶段七完成标准**：拥有自己的 C++ Pass、自定义操作与 Lowering；能把张量计算运行到 CPU，并在受支持的目标上完成一次调度与硬件映射；能解释变换合法性、内存语义及代码生成边界。学习产物包含实现、IR 测试、数值结果与关键源码位置。无需读完所有 Dialect 或先学完整 LLVM 后端再进入项目；能满足阶段八实际需求时即可迁移到项目。

**主要资料**：[MLIR Getting Started](https://mlir.llvm.org/getting_started/)、[Using mlir-opt](https://mlir.llvm.org/docs/Tutorials/MlirOpt/)、[Toy Tutorial](https://mlir.llvm.org/docs/Tutorials/Toy/)、[Pattern Rewriting](https://mlir.llvm.org/docs/PatternRewriter/)、[Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)、[Bufferization](https://mlir.llvm.org/docs/Bufferization/)、[Transform Dialect Tutorial](https://mlir.llvm.org/docs/Tutorials/transform/)。按小节使用，同版本官方示例和测试是具体 API 的依据。

## 阶段八：编译器与算子综合项目

**目标**：把图优化、调度、Lowering、Runtime 与已有 CUDA/Triton 算子连接起来，形成可以演示、复现和继续扩展的小项目。在现有机器上先完成软件执行链，真实加速器项目出现后再替换后端。

### 8.1：确定一条实现主线与明确的支持范围

选择 TVM 或 MLIR 其中一条作为主实现，不同时维护两套完整后端。两层 MLP 用于快速验证接口，但不限定最终项目：基线测量后从已有 `OperatorEngine`、CUDA/Triton 算子或单卡模型代码中，选一个真实的算子/子图瓶颈（例如重复的中间张量读写或已测得的启动开销）作为项目问题。没有测到瓶颈时，先把项目定义为功能接入与正确性验证，不能为追求加速而虚构问题。若阶段六已有可行项目，可提前开始 TVM 版本；不必等 MLIR 全部内容学完。

先直接构造图，确定基线与可验证的优化假设，跑通后再决定是否需要框架前端入口（PyTorch 导出或 ONNX 二选一）。写清支持的算子、shape、dtype、布局与设备；先静态 shape、FP32，精度和动态维度扩展仅在具体需求出现时增加。

### 8.2：接入一个已有算子，形成编译与运行闭环

**优先接入对象**：从所选计算图实际调用的算子中选择已有 CUDA/Triton GEMM、Softmax 或简单融合算子的一项，复用 6.4 的最小外部调用。需要时提取一个小型独立 kernel，不重构整个 OperatorEngine，也不把首个目标设为完整 FlashAttention。

**必须走通的链路**：

```text
模型或手工构图
  -> 语义与 shape 检查
  -> 一项自定义图优化 / 模式识别
  -> 选择生成实现或外部算子
  -> Lowering 成实际调用 / 代码
  -> Runtime 传参、内存与 stream 处理
  -> 执行、数值对齐与计时
```

对于 TVM，先完成一个外部函数/算子的调用，再按需扩展为子图划分与 BYOC；对于 MLIR，先降低为受支持的外部函数调用并补运行库包装。接入方式以选定版本为准。两种路径都要明确 ABI、shape/stride/dtype/device、所有权和同步要求。

给出可解释的后端选择规则：满足已支持的 shape/dtype/layout 才走自定义路径，其余走明确的基线路径，或报告尚不支持；避免静默误算。未来接 FPGA/NPU 时，再把该边界替换为真实 Runtime/驱动接口。

### 8.3：性能归因与交付

**三组对照**：

| 版本 | 回答的问题 |
| --- | --- |
| 参考执行 / 编译器基础流水线 | 结果是否正确，基本执行成本是多少 |
| 增加指定图优化或调度 | 该变换实际改变了哪些 kernel、内存或执行开销 |
| 接入自定义算子 | kernel 局部收益能否传递到整个计算图 |

逐项验证融合、调度、外部调用或内存改动，避免同时开启多种优化后无法归因。分别记录编译/调优时间、稳定执行时间、kernel 时间、端到端时间及必要的拷贝开销。比较同一 dtype、输入与计时边界；CPU 路径不与 GPU kernel 时间直接计算加速比。

**项目验收**：

1. 用一条命令完成小规模正确性验证，覆盖普通 shape、尾块和不支持输入的处理。
2. 保存关键层 IR、调用接口、生成代码或执行轨迹，能解释一项优化从哪里来。
3. 展示算子时间与端到端时间的差异；如果没有收益，能定位调度、拷贝、启动或实现本身的限制。
4. 形成 README、环境记录、原始结果和短报告；能够指出新增一个算子需要改哪些模块。

**真实项目驱动的扩展**：接入实验室已有 FPGA/NPU 后端，学习实际算子覆盖、片上存储、DMA、命令提交与同步；先用真实协议完成最小算子，再扩大模型范围。没有硬件/协议时可写接口约定或功能模型，但不把它作为真实后端支持或性能证据。

**主要资料**：[TVM Bring Your Own Codegen](https://tvm.apache.org/docs/how_to/tutorials/bring_your_own_codegen.html)、固定版本中的外部调用/Runtime 示例，以及阶段七已经使用的 Dialect Conversion 和执行示例。资料服务于所选项目，不另开一条完整框架学习支线。

## 阶段六～八的执行方式与选修边界

**每个小节按四步推进**：先给出原理、具体 shape 和一个可手算例子；阅读提问后确定最小实现；由学习者参与关键设计与代码；再检查正确性、IR 和必要的性能结果。完成一次复盘后，再经确认进入下一小节。本次只确定路线，不提前生成全部课程或替学习者完成核心实现。

**源码阅读的深度**：每次沿一个具体问题追踪“入口 -> IR 数据结构 -> 分析/改写实现 -> 测试 -> 生成结果”。以能解释和修改一个机制为目标，不按目录通读整个 TVM、LLVM 或 Triton。

**时间安排**：以小节产物和理解程度推进，不设“几周必须学完”的硬期限。遇到同类内容不重复完成三套实现；阶段六学会的调度和测试方法带入阶段七，阶段八复用已有代码。

**防止知识陷阱的停止规则**：

1. 每节开始先确定一个具体问题和一个可验证产物。已经能独立解释、修改和验证的内容直接跳过；不为追求知识体系完整而追加同类教程或 API 清单。
2. 理论只学到能够支持当前实现、理解合法性和定位错误的深度。遇到新概念先判断它是否阻塞当前问题，非必要知识放入选修清单，不能沿前置知识无限递归。
3. 先跑通，再预测并改变一项真实行为，最后看结果。单纯看完视频、读完源码、复现官方教程或生成 IR 不算掌握；至少独立改变一个输入、改写规则或调度条件，检验自己的预测。
4. 避免所有内容都做 Benchmark：语义、Pass 合法性以 IR、正反例和数值测试为主；只有涉及执行性能的变换才使用控制变量和 profiler。优化失败但原因有证据照样可以结束该实验。
5. 环境问题先做有边界的诊断，若不能运行就切换到当前可验证的任务，并保留未完成项；不以大段理论、模拟硬件性能或换工具补偿资源缺失。到达阶段验收条件立即进入下一任务；实际项目出现时优先按项目需求调整学习顺序。

| 内容 | 当前安排与触发条件 |
| --- | --- |
| 词法/语法分析、完整通用语言前端 | 先知道位置；有 DSL/前端任务时再系统展开 |
| CFG、支配关系、数据流分析、别名与依赖分析 | 从具体 Pass 按需加深，不要求一开始手写所有算法 |
| 动态形状与符号 shape | 静态主案例跑通后，选择一个动态维度小范围扩展 |
| Tensor Core tensorization、复杂流水与自动调优成本模型 | 基础调度和正确性稳定后选一项深入 |
| LLVM 指令选择、寄存器分配、机器调度 | 先理解后端职责；有低层代码生成问题时再学习 |
| Triton 编译器源码修改 | 阶段七后选一个已观察到的 layout/Lowering 问题深入，作为延伸项目 |
| torch.compile / Inductor、IREE、StableHLO 等其他栈 | 核心主线完成后按目标项目选择一种，不并行铺开 |
| 完整模型量化、多卡通信、分布式推理 | 保留阶段五资料，实际项目需要时恢复 |
| FPGA/NPU 真实后端 | 有可访问项目、协议和硬件后推进；不阻塞当前学习 |

**接下来的第一个里程碑**：完成 6.0 的 TVM 最小运行实验，再在 6.1 用真实编译器观察、预测并验证一个合法改写。已具备的 C++ IR 基础快速核对，不重写小型编译框架。进入 TensorIR 调度后，每增加一项知识都须服务于实际变换或执行问题。

> 当前背景与学习约定：
> 1. 主线为 AI 编译器与算子开发，已有阶段一～四的 C++、架构桥接、CUDA/Triton 算子与 IR 阅读基础。
> 2. TVM 已做过架构入门、Docker 环境、Schedule 优化 GEMM 与 ONNX 编译运行；MLIR 尚未系统学习。
> 3. 阶段五学习到 5.6 后暂停，今后结合实际项目与多卡资源恢复，不将理论推演记为多卡实测。
> 4. 当前按阶段六 TVM、阶段七 MLIR、阶段八综合项目推进，使用 CPU/单 GPU 完成主要实验。
> 5. 讲解以具体数据、shape、执行过程和底层动机为主；关键设计、实现与实验保留学习者参与，完成一个小节并复盘后再推进。
> 6. 区分已经测得的结果、理论分析、计划任务和未验证事项；性能结论限定在实际环境、输入与测量范围内。
