# Question

### 1. Naive Attention 的完整计算过程是什么？

```
S = QKᵀ / sqrt(D)
P = softmax(S)
O = P@V
```

其中：

- `S` 是查询和键之间的匹配分数；
- `P` 是每一行经过 Softmax 后的注意力概率
- `O` 是使用概率对 V 加权求和后的最终输出。

此外，因果模式还需要在 Softmax 之前，把未来位置的分数设置为负无穷

### 2. Q、K、V 的 Shape 都是 `[B,H,N,D]`，那么：

```
Kᵀ 的最后两个维度是什么？—— [B, H, D, N]
S 的 Shape 是什么？—— [B, H, N, N]
O 的 Shape 是什么？—— [B, H, N, D]
```

注意这里只交换 K 的 `N` 和 `D`，不会交换 Batch 和 Head

### 3. Softmax 应该沿哪个维度计算？为什么？如果沿错维度，会产生什么含义？

softmax 应该沿着最后一个维度，也就是键位置进行计算：`softmax(S, dim=-1)`

对于某一个查询位置，它需要在全部键位置之间分配注意力，含义是“多个键竞争同一个查询”，因此P的每一行概率之和应该为1

如果沿错维度，就会变成每一列的概率和为1，含义变成了“多个查询竞争同一个键”，不符合注意力机制的定义

### 4. 为什么要除以 `sqrt(D)`？它解决的是什么问题？

因为Q和K的点积包含D项的累加，当D较大时候，点积数值可能会变得很大，使得softmax过早的接近0或1

因此采用除以sqrt(D)的方法来缩小分数范围，这样可以使得softmax更加稳定，避免梯度过早饱和

### 5. 因果注意力和非因果注意力有什么区别？

因果注意力中，查询位置i只能查看j <= i的内容，不能查看 j>i，也就是不能“偷看未来”，但可以看见过去和自己。

mask应该在softmax之前处理，只有这样，才能保证被遮住的位置最终概率为0

```
未来位置的 Score → -∞
Softmax(-∞) → 0
```

非因果注意力可以查看所有的键

### 6. 为什么 Naive Attention 会产生平方级显存？

如果序列长度从 `1024` 变成 `2048`，`S+P` 的容量会变成多少倍？

由于每个查询都要和全部的键作比较，所以 N个查询 * N个键 = N²个分数

因此 S：[B,H,N,N]、P：[B,H,N,N]，两者都随 `N²` 增长，所以 `S+P` 容量变成原来的 4 倍。

### 7. 计算下面配置的中间矩阵容量：

```
B = 2
H = 8
N = 1024
dtype = FP16
```

分别计算：

```
S 的容量：2 * 8 * 1024 * 1024 * 2B = 32MB
P 的容量: 2 * 8 * 1024 * 1024 * 2B = 32MB
S + P 的容量: S + P = 64MB

此外，如果还统计输出 O，需要另外加上：
O = 2 × 8 × 1024 × 64 × 2 字节
  = 2 MiB
因此该配置的 S+P+O 是 66 MiB
```

### 8. 本次 Triton 实现为什么拆成三个 Kernel？这三个 Kernel 分别做什么？

本次实验是故意把计算拆成三个阶段的：

- Score Kernel：Q、K -> S
- Softmax Kernel: S -> P
- Output Kernel: P、V ->O

这样做的好处是：更容易理解，更方便进行阶段测试，也方便定位错误

代价是必须把S和P写入显存，然后再读回来，因此并不是最节省显存和流量的实现。后续会对其进行优化

### 10. 为什么说 Naive Attention 是后续 FlashAttention 的正确性基准？

因为当前我们会严格按照数学公式分成三个清晰的步骤，显示保留S和P，因此可以分别检查：

- Score 是否正确；
- Mask 是否正确；
- 每一行概率和是否为 1；
- 被遮罩位置概率是否为 0；
- 最终 O 是否正确。

后续FlashAttention虽然不再完整保存S和P，但数学结果应该与Naive Attention一致。

因此 Naive Attention 可以作为更复杂融合实现的标准答案

### 11. 本次实验如何测试峰值显存？这个指标不能证明什么？

本次测试显存峰值的方法步骤如下：

```py
# Q,K,V 已经提前创建，不算做本次算子的格外显存
torchtorch.cuda.synchronize()

# 清楚之前记录的峰值
torch.cuda.reset_peak_memory_stats()

# 记录执行前已经分配的显存
before = torch.cuda.memory_allocated()

# 执行一次 Attention
output = attention(q, k, v)

# 等待GPU完成计算
torch.cuda.synchronize()

# 获取执行期间出现过的最高显存
memory_peak = torch.cuda.max_memory_allocated()

# 计算算子额外产生的峰值显存
peak_delta = (
    torch.cuda.max_memory_allocated() - before
)
```

预热和Triton编译应该在正式统计之前完成

这个方法可以测量算子额外产生的已分配的显存峰值，但不能证明：

- 实际显存读了多少字节
- 缓存命中率
- 是否发生寄存器溢出
- 占用是否过低
- GPU计算受限还是带宽受限

这些还需要采用 Profiler 工具进一步验证

### 12. 如何区分“算法正确”“工程可用”和“性能优秀”？

算法正确：结果符合数学定义，并且能与Pytorch Reference对齐

工程可用：在算法正确的基础上，能够处理不同的Shape，Dtype，非对其长度，因果mask和错误输入，并具有明确的输入限制

性能优秀：在算法正确，工程可用的基础上，需要在目标硬件和主要shape上做到稳定降低延迟，显存容量以及显存流量。

本次实验已经真正到达了算法正确和工程可用，但仍然显示保存S和P，所以不能称作最终的高性能attention

## 总结

我实现了一个显式物化中间矩阵的 Triton Naive Attention。它分成三个 Kernel，依次计算 `S=QKᵀ/sqrt(D)`、沿键维度进行行 Softmax 得到 P，再计算 `O=PV`。

因果模式会在 Softmax 前把未来位置设为负无穷。实现通过了 73 项正确性测试，并与 PyTorch 进行了延迟、TFLOPS 和峰值显存对比。

实验发现 S 和 P 的 Shape 都是 `[B,H,N,N]`，因此中间显存随序列长度平方增长。例如本次配置下，N 从 1024 增加到 2048，S+P 从 64 MiB 增加到 256 MiB。

这个版本的意义不是追求最终性能，而是建立清晰、可靠的正确性基准，并暴露显式中间矩阵带来的容量和访存问题，为后续 FlashAttention 提供对照。

后续实现不是简单复现 Attention，而是使用分块和在线 Softmax，把 Score、Mask、Softmax 与 PV 融合到一个 Kernel 中，避免显式保存 N×N 的 S 和 P，从算法结构上降低峰值显存和显存流量。这使它具备真正的 FlashAttention 性能基础。

完成后我会与 PyTorch 和 Triton Naive Attention 对比延迟、TFLOPS 和峰值显存。不过我会区分教学实现和工业级实现：只有实验数据支持的 Shape 才能称为性能优秀，寄存器压力、occupancy 等底层原因还需要 Profiler 验证。
