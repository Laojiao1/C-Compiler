# 1. C++ unique_ptr

**思考一个问题**：C++ 为什么能在没有 GC（垃圾回收）的情况下，依然保持极高的性能和绝对的内存安全？

答案就在于**生命周期管理**。

下面将基于几个经典场景，逐步引出 C++ 中的智能指针

## 一：裸指针存在的严重问题（没有生命周期管理）

在底层开发（如算子内存分配）中，如果使用最原始的 `new/delete`，极易引发内存泄漏

假设用最古老的 C 语言思路写了这段代码：

```cpp
void process_tensor() {
    // 1. 在堆（Heap）上申请了 1GB 的显存/内存，拿到裸指针
    float* tensor_data = new float[256 * 1024 * 1024]; 
    
    // 2. 突发情况：比如除以 0 或者语法树解析失败
    if (error_happened) {
        return; // 【灾难发生】函数提前退出，底下的 delete 永远不会被执行！
    }
    
    // 3. 正常情况下的释放
    delete[] tensor_data; 
}
```
**问题在哪？** 裸指针 `tensor_data` 只是一个毫无感情的整数（存着地址）。当代码因为 `error_happened` 提前 `return` 时，函数结束了，那 1GB 的内存永远被丢在了堆里，没人管了（内存泄漏）。这就是**没有生命周期管理**的下场。

## 二：栈（Stack）的特殊机制 —— RAII 的灵感来源
C++ 编译器有一条不可违背的铁律：**作用域 `{ }` 就是局部栈对象的“生死线”**。

```cpp
class MyGuard {
public:
    MyGuard() { std::cout << "出生\n"; }
    ~MyGuard() { std::cout << "死亡\n"; }
};

void process_tensor() {
    { // 开始
        MyGuard guard; // guard 是分配在栈（Stack）上的局部对象
        
        if (error_happened) {
            return; // 就算在这里提前退出...
        }
    } // 结束
}
```
在这个例子中，只要 `guard` 离开了它所在的 `{ }` （不管是因为正常结束、还是提前 `return`、或者是抛出异常），编译器**必定**会自动触发它的析构函数 `~MyGuard()`。

## 三：把指针关进栈里（初级智能指针）
既然栈变量死的时候必然会触发析构，那只要我们把堆上的裸指针放进栈对象里，不就不需要手动 `delete` 了吗？

```cpp
class SmartPointer {
    float* ptr_; // 偷偷把裸指针藏在肚子里
public:
    SmartPointer(float* p) { ptr_ = p; }
    ~SmartPointer() { delete[] ptr_; } // 死亡时，顺手把肚子里的内存释放了
};

void process_tensor() {
    // p 活在栈上，但它肚子里装着堆上的 1GB 内存
    SmartPointer p(new float[256 * 1024 * 1024]); 
    
    if (error_happened) {
        return; // 提前退出？完全没问题！
        // 离开作用域时，p 被销毁，强制调用 ~SmartPointer()，内存安全释放。
    }
}
```
这就是 **RAII（资源获取即初始化）**。通过绑定局部对象的生命周期，把手动释放的责任全部推给了编译器。

## 场景四：克隆带来的问题（为什么要禁掉 Copy）
初级智能指针看起来完美，但如果被不小心复制，会导致整个系统崩溃。

```cpp
void bad_code() {
    SmartPointer p1(new float[10]); // p1 肚子里装了指针 0xAAA
    SmartPointer p2 = p1;           // p2 把 p1 复制了一份！大家肚子里都是 0xAAA
    
} // 重点来了！离开作用域，大家都要被销毁！
```
**回顾一下**：

1. `p2` 先死，执行 `delete 0xAAA`，内存被回收。
2. 接着 `p1` 死，再次执行 `delete 0xAAA`。
3. **最后！Double Free（重复释放），程序直接崩溃闪退。**

**怎么解决？** 

- 直接从源头掐断，不准复制！ 

```c++
// 我们强行规定：同一块内存，只能有一个主人（独占所有权）
unique_ptr(const unique_ptr&) = delete; 
```

## 场景五：不复制，但转移（移动语义 move）
既然不能复制，假如我想把这块内存传给另一个函数去处理怎么办？ 

**答案是：移动语义 move**

```cpp
void pass_baton() {
    SmartPointer p1(new float[10]); // p1 是主人 (0xAAA)
    
    // 我们不复制，用 std::move 告诉编译器：强行转换为右值，触发“偷窃”！
    SmartPointer p2 = std::move(p1); 
    
    // 偷窃过程（在移动构造函数中发生）：
    // 1. p2 把 0xAAA 拿走。
    // 2. p1 的肚子立刻被设为 nullptr（空）。
} 
// 离开作用域：
// p2 析构 -> delete 0xAAA (正常释放)
// p1 析构 -> delete nullptr (C++ 规定 delete 空指针是绝对安全的)
```
`std::move` 在底层没有移动任何真实数据，它把一个左值强行“伪装”成右值，从而触发资源窃取，完成了一次**指针的交换与清空**（近零开销）。

这里我们需要好好讲解一下 `std::move`，但是再讲之前，我们需要先了解一下 什么是左值、什么是右值

> **补充知识点：什么是左值？什么是右值？**
>
> 在 C++11 之前，每次传递对象都会触发极其昂贵的“深拷贝（Deep Copy）”。为了解决这个问题，语言引入了右值引用的概念。其核心逻辑是：**如果我发现一个对象“马上就要消亡了”，那我就不拷贝它，而是直接把它的底层内存指针“偷”过来。** 区分谁能被偷、谁不能被偷，就是左值和右值的核心意义。
>
> #### 1. 左值 (Lvalue - Locator Value)
>
> - **本质**：它在内存栈中有一个明确的、持久的物理地址，你可以反复通过这个名字去访问它
>
> - **判别法**：能不能用 `&` 对它进行取地址？能取地址的，就是左值
>
> - **代码示例**：
>
>   ```c++
>   int a = 10;       // 'a' 是左值，你可以对它执行 &a
>   Tensor t("X");    // 't' 是左值，它安稳地活在栈上，生命周期直到作用域结束
>   ```
>
> - **拷贝策略**：因为左值还要继续存活，别人可能还要用它，所以**绝对不能偷它的资源**，只能老老实实对它进行“深拷贝”
>
> #### 2. 右值 (Rvalue - Read Value / Temporary)
>
> - **本质**：它通常只是 CPU 寄存器里的一个**临时计算结果**，或者表达式产生的一个**临时对象**。一旦这行代码执行结束，它立马就会灰飞烟灭。
>
> - **判别法**：**无法**用 `&` 对它取地址。
>
> - **代码示例**：
>
>   ```c++
>   int a = 10;
>   int b = 20;
>   // 'a + b' 算出来的那个结果 30，在赋值给 c 之前，就是一个右值。你无法对 &(a+b) 取地址。
>   int c = a + b; 
>   
>   Tensor t = Tensor("Y");  // 'Tensor("Y")' 是一个临时构建的右值对象，一旦赋值完成就死了。
>   ```
>
> - **拷贝策略（窃取）**：既然右值马上就要死了，里面包含的（比如几十 MB 的堆内存指针）直接销毁太浪费了。我们完全可以触发**移动构造（Move Constructor）**，光明正大地把它的底层指针“偷”过来据为己有，反正它死后也不会有人再访问它。

回到最初的问题：我想把一块内存传给另一个函数去处理，但是由于这块内存存放的是左值，我们无法去“偷”他的资源，该怎么办？

这时候就需要用到 `std::move`：

- 比如我需要复制一份`t1`：调用`std::move(t1)` 时，它其实在底层**什么都没做（不发生任何真实移动）**，仅仅进行了一个类型转换 —— 把一个坚挺的左值 `t1`，强行转型成了一个右值（引用 `T&&`）
- 编译器一看 “是个右值了”，就会立刻激活后续的构造函数，把 `t1` 的资源合法地窃取走

## 总结

把这四个场景串起来， 就是`unique_ptr` 的本质思想：

1. **裸指针**太危险，动辄内存泄漏
2. 于是我们用**栈对象的生命周期（RAII）**把它包起来，死的时候自动释放
3. 但包起来后怕被别人**复制**，而导致两次释放（Double Free），所以我们 **禁止 Copy**
4. 禁止 Copy 后没法传递了，于是我们采用另一种方法： **移动（Move）**—— 它只传递，不复制

## 代码

### my_unique_ptr.hpp

```c++
#pragma once

#include <utility> // for std::move, std::exchange

namespace ai_infra {

// 模板，代表这个删除器可以处理任意类型 T 的指针
template <typename T> 
struct DefaultDeleter { // 默认的 Deleter，后续可以根据需要进行扩展
    void operator()(T* ptr) const { // 重载括号运算符，以后可以直接使用 DefaultDeleter<int> del; del(ptr);
        if(ptr) {
            delete ptr; // delete：1.调用析构函数（如果有）2. free
        }
    }
};
    
// 定义带有自定义 Deleter 模板参数的 unique_ptr
template <typename T, typename Deleter = DefaultDeleter<T>>
class unique_ptr {
private:
    T* ptr_; // 裸指针
    Deleter deleter_; // 删除器实例
    
public:
    // ----- 构造与析构 -----
    // constexpr：表示在编译期就能算出来，用于极致优化
    // noexcept：向编译器保证这个函数绝对不会抛出异常。编译器看到它，就会省去很多生成异常处理栈展开的底层代码
    constexpr unique_ptr() noexcept : ptr_(nullptr) {}
    
    // 显式指针构造函数，用于获取资源
    explicit unique_ptr(T* p) noexcept : ptr_(p) {}
    
    // 析构函数
    ~unique_ptr() {
        deleter_(ptr_); // 利用 deleter_ 安全释放 ptr_
    }
    
    // ----- 独占所有权 -----
    // 显式禁止 “拷贝构造函数” 和 “拷贝赋值运算符”，防止重复释放
    unique_ptr(const unique_ptr& other) = delete;
    unique_ptr& operator=(const unique_ptr& other) = delete;

	// ----- 资源转换（移动语义）-----
    // 这里的 other 代表一个“即将消亡的值”（比如临时变量，或者被 std::move 强制转换的变量）
    // std::exchange(a, b)：把 a 的旧值返回，然后把 b 赋值给 a。在这里，它等价于：this->ptr_ = other.ptr_; other.ptr_ = nullptr;
    unique_ptr(unique_ptr&& other) noexcept 
    : ptr_(std::exchange(other.ptr_, nullptr)), 
      deleter_(std::move(other.deleter_)) {}
    
    // 移动赋值运算符
    // 注意逻辑：先释放自己原有的资源，再去偷 other 的资源
    unique_ptr& operator=(unique_ptr&& other) noexcept {
        if(this != &other) { // 防止自赋值
            deleter_(ptr_); // 先释放自己的资源
            // 偷 other 资源
            ptr_ = std::exchange(other.ptr_, nullptr);
            deleter_ = std::move(other.deleter_);
        }
        return *this;
    }
    
    // ----- 底层指针操作 -----
    // 重载解引用，目的是为了让它用起来像原生指针一样
    T& operator*() const { return *ptr_; }
    T* operator->() const { return ptr_; }
    
    // 获取底层裸指针
    T* get() const { return ptr_; }
    
    // 实现 reset 逻辑：注意要先释放旧资源，然后接管新指针
    void reset(T* p = nullptr) noexcept {
        T* old_ptr = std::exchange(ptr_, p);
        deleter_(old_ptr);
    } // 这里不直接 deleter_(ptr_); ptr_ = p; 的原因是为了防止重置同一个指针（如 p1.reset(p1.get())）导致先被释放的 Bug
    
    // 实现 release 逻辑：不再管理该资源，由调用者手动 delete
    T* release() noexcept {
        // 放弃所有权，拿走当前指针，内部置为空，并把拿走的指针返回给外界
        return std::exchange(ptr_, nullptr);
    }
};
    
} // namespace ai_infra
```

## 面试题

### 请谈谈你对 C++ 智能指针和内存管理的理解？

#### 一、点出核心 —— RAII 与确定性
> **参考回答**：
>
> “C++ 内存管理的核心哲学是 **RAII（资源获取即初始化）**。在 AI 底层系统（如算子开发）中，我们追求绝对的性能和可控性，因此不能依赖像 Java 那样有停顿的垃圾回收器（GC）
>
> RAII 的精髓在于：把堆内存、CUDA 显存、互斥锁等系统资源的生命周期，强行绑定到栈上局部变量的作用域中。利用 C++ **离开作用域必定触发析构函数**的确定性机制，实现了无死角、具备异常安全（Exception Safe）的自动资源回收”

#### 二、深度剖析 —— 独占与零开销
> **参考回答**：
>
> “在使用场景中最推荐的是 `std::unique_ptr`，它的主要标志是**‘独占所有权’**与**‘零开销’**
>
> 1. **关于独占**：在底层源码实现中，它通过 `= delete` 显式禁用了拷贝构造和拷贝赋值，从语法层面上彻底杜绝了两个指针指向同一块内存而导致的 Double Free（重复释放）问题。巧妙地把一个**运行时灾难**，提前拦截成了**编译期错误**
> 2. **关于流转**：当需要转移某个计算图节点的所有权时，可以采用 `std::move` 强制将其转换为右值，触发**移动语义（Move Semantics）**。底层仅仅是做了一个极低成本的指针接管，并将原对象的指针安全置空（置空操作通常用 `std::exchange` 实现）
> 3. **关于零开销**：如果使用默认删除器，`unique_ptr` 在运行时的内存大小和普通的裸指针（通常是 8 字节）完全一致，没有任何性能损耗”

#### 三、拓展 —— 自定义 Deleter 的系统级应用
> **参考回答**：
>
> 除了管理普通的堆内存，`unique_ptr` 更强大的地方在于它是一个泛型的资源守卫。它可以传入自定义的 Deleter（删除器），用来管理异构计算的资源
>
> 比如我们在写 Triton 或 CUDA 底层扩展时，我可以定制一个内部调用 `cudaFree` 的删除器；
>
> 在处理网络层时，可以定制一个调用 `fclose` 或关闭 Socket 的删除器。
>
> 它统一了整个系统的资源生命周期流转

### 可能追问的小细节：

**为什么移动构造/赋值函数通常要加 `noexcept`？**

> `noexcept`的含义是告诉编译器，这个语句不会发生异常，放心编译即可
>
> 因为在转移资源所有权（仅仅是挪动几个指针）的过程中，逻辑上不应该也不可能抛出异常。加上 `noexcept` 可以让标准库容器（如 `std::vector`）在扩容重分配时，放心地调用移动构造函数而不是退化为缓慢的拷贝构造函数。

**在手写移动赋值 `operator=` 时，最容易忽略什么？**

> 有两个致命点：
>
> - 忘记检查**自我赋值**（`if (this == &other)`）。如果自己移给自己，先把当前资源释放了，后面就全乱套了
> - 应该**先释放自己现有的资源**再去接管别人的资源，防止现有资源泄漏
