# 2. C++ 算子工厂

## 引入

在深度学习框架（如 PyTorch 的 ATen 库）中，当用户在 Python 层调用 `torch.add(a, b)` 时，底层 C++ 需要根据张量 `a` 的 `Device`（CPU 或 CUDA）以及 `Dtype`（FP32 或 INT8），分发到对应的底层硬件算子实现。

如果采用传统的流程控制，分发中心的代码会写成这样：

```cpp
Tensor add(const Tensor& a, const Tensor& b) {

    if (a.device == "CPU" && a.dtype == "FP32") return add_cpu_fp32(a, b);

    else if (a.device == "CUDA" && a.dtype == "FP32") return add_cuda_fp32(a, b);

    // ... 剩下 100 种组合

}
```

**底层缺陷**：每当新增一种硬件加速器（如 NPU、TPU）或数据类型，就必须修改这段核心的分发代码，并重新编译整个框架核心库。这严重违反了开闭原则（Open-Closed Principle），导致框架极难扩展。

### 解决方式：全局注册表查表机制

建立一个全局的**算子注册表（OpRegistry）**。

- **查表替换分支**：运行时直接通过字符串 Key（如 `"add_CPU_FP32"`）去全局哈希表里查函数指针，直接执行。彻底消灭 `if-else`。
- **解耦核心**：只要保证每个算子在框架启动时，能把自己“塞”进这张表里，核心框架层就永远不需要知道具体有哪些硬件接入了。实现了架构级别的即插即用。

现在：我们辛辛苦苦搭好了 `OpRegistry`，但最终还是要在 `main()` 函数里这么写：

```c++
int main() {

    OpRegistry::get_instance().register_op("add_CPU_FP32", add_cpu_fp32);

    OpRegistry::get_instance().register_op("add_CUDA_FP32", add_cuda_fp32);

    // ...

}
```

**缺陷**：还是太冗余！只要第三方硬件团队（比如 NPU）想新加一个算子，他们还是得跑到主干仓库的 `main()` 函数里强行插一行注册代码。中心化的代码修改（强耦合）依然存在。

### 静态变量初始化时间线

要想让主框架完全不知道底层算子的存在，算子就必须学会**自我注册**。

在 C++ 中，生命周期最长、执行最早的并不是 `main()` 函数，而是**全局静态变量**。 C++ 运行时会在跳转执行 `main()` 的第一条汇编指令之前，扫描所有目标文件（`.o` / `.obj`），并**自动依次调用所有全局对象的构造函数**

基于此，我们可以设计一个专用的“自动注册助手”类（Registrar）

1. 在它的**构造函数**内部，调用 `OpRegistry::get_instance().register_op()`
2. NPU 团队在他们自己的 `npu_add.cpp` 文件的全局作用域中，定义一个这个具有“助理”功能的全局静态对象

**结果**：当进程被 OS 拉起时，C++ 运行时会默默构建这个全局助手对象，从而触发了它的构造函数，顺理成章地将 NPU 算子塞进哈希表中，当 `main()` 函数的第一行 `std::cout` 打印出来时，哈希表早就已经被各个模块自动填满了！

代码：

```c++
#include <iostream>
#include <string>
#include <unordered_map>
#include <functional>
#include <stdexcept>

// 模拟 Tensor 数据结构
struct Tensor {
    std::string device; // "CPU" or "CUDA"
    std::string dtype;  // "FP32" or "INT8"
    float data;         // 简化版，实际为数据指针
};

// 定义底层算子函数的统一签名
using OpFunc = std::function<Tensor(const Tensor&, const Tensor&)>;

// ----- 架构层 -----

// 全局算子注册表 (Registry)：采用经典的 Meyers 单例模式
class OpRegistry {
private:
    // 定义哈希表 registry_：
    // Key 是字符串（描述算子的特征签名，例如 "add_CPU_FP32"）
    // Value 是对应的函数指针 OpFunc
    std::unordered_map<std::string, OpFunc> registry_;

    // 私有化构造函数，阻止外部 new 实例化
    OpRegistry() = default;

public:
    // 禁用拷贝和赋值操作，防止破坏单例，严防多重注册表导致的数据不一致
    OpRegistry(const OpRegistry&) = delete;
    OpRegistry& operator=(const OpRegistry&) = delete;

    // 获取全局唯一实例的引用
    static OpRegistry& get_instance() {
        // C++11 标准保证了局部静态变量初始化的线程安全性
        static OpRegistry instance;
        return instance;
    }

    // 实现注册接口
    // 将传入的 name 和 func 存入 registry_ 中
    void register_op(const std::string& name, OpFunc func) {
        registry_[name] = func;
    }

    // 实现分发接口：根据 name 去 registry_ 里查找对应的函数并返回
    OpFunc get_op(const std::string& name) {
        auto it = registry_.find(name); 
        if (it == registry_.end()) { // 如果找不到，抛出 std::runtime_error 异常，并带上出错的 name 提示。
            throw std::runtime_error("Operator not found: " + name);
        }

        return it->second;
    }
};

// 自动注册助手类 (Registrar)：将函数的注册动作封装到对象构造阶段，利用 C++ 静态变量初始化期发起注入
class OpRegistrar {
public:
    // 构造函数：在这个构造函数内部获取单例，并将 name 和 func 注册进去
    OpRegistrar(const std::string& name, OpFunc func) {
        OpRegistry::get_instance().register_op(name, func);
    }
};

// ----- 工作区 -----
// 进行场景模拟：以下代码完全可以写在一个完全独立的 add_cpu.cpp 中
// 他们既不包含也不修改 main.cpp，完全实现了代码解耦

// 1. 自定义底层硬件算子实现
Tensor add_cpu_fp32(const Tensor& a, const Tensor& b) {
    std::cout << "[Backend: CPU FP32] Executing Add (Mem Addr: 0x...) " << std::endl;
    return Tensor{"CPU", "FP32", a.data + b.data};
}

// 完成算子自注册
// 在全局作用域定义一个静态的 OpRegistrar 对象，把 "add_CPU_FP32" 和 add_cpu_fp32 的函数指针传进去
// 注意：利用 static 关键字触发编译期的静态分配
static OpRegistrar add_cpu_fp32_registrar("add_CPU_FP32", add_cpu_fp32);

// 主函数
int main() {
    std::cout << "--- Main System Booting ---" << std::endl;
    
    Tensor a{ "CPU", "FP32", 1.5f };
    Tensor b{ "CPU", "FP32", 2.0f };

    try {
        // 主框架此时根本不知道 add_CPU_FP32 是谁写的，直接从哈希表里按名字提货！
        auto op = OpRegistry::get_instance().get_op("add_CPU_FP32");
        Tensor result = op(a, b);
        std::cout << "Result: " << result.data << std::endl;
    } catch (const std::exception& e) {
        std::cerr << "Fatal Error: " << e.what() << std::endl;
    }

    return 0;
}
```

## 问题

思考一个问题：如果沿用之前的写法，当我们同时开发 CPU 和 CUDA 两个加法算子时，代码会变成这样：

```cpp
static OpRegistrar cpu_add_reg("add_CPU", add_cpu);

static OpRegistrar cuda_add_reg("add_CUDA", add_cuda);

// 如果有 1000 个算子呢...？
```

**带来的问题**：在数千个算子的大型 C++ 项目中，如果A写了个静态变量叫 `add_reg`，B碰巧也起名叫 `add_reg`，一旦合入主分支编译，编译器立刻就会报 `Redefinition Error`（变量重复定义）。这种强依赖人工去维护唯一命名的方式，是极度危险且反直觉的。

因此我们必须设计一个宏 `REGISTER_OP(name, func)`，让算子开发人员**只传业务数据，完全接触不到底层静态变量**。

要想自动生成不冲突的变量名，我们需要使用 C++ 预处理器（Preprocessor）的两个方法：

1. `__COUNTER__`：编译器内置的一个特殊宏，每次出现时，它在编译期的值都会自动 `+1`（比如 0, 1, 2...）。
2. `##`（Token Pasting 拼接符）：在宏定义中，它可以把左右两边的字符在编译期**硬生生粘合在一起**。

只要把 `__op_reg_` 和 `__COUNTER__` 粘合起来，我们就能在编译期源源不断地生产出 `__op_reg_0`, `__op_reg_1` 这种绝对不会重复的隐藏静态变量！


代码解析：

- **`__COUNTER__`**：这是编译器自带的内置宏。你在代码里每用它一次，它的值就会偷偷加 1（从 0 开始：0, 1, 2...）。它是我们保证命名绝对不重复的底层算力。
- **`##`（Token Pasting 运算符）**：宏拼接符。它的作用是把左右两边的文本死死地“焊”在一起。比如 `A ## B` 在编译后直接变成文本 `AB`。

## 继续升级

对于追求极度榨干硬件性能的算子工程师来说，框架的每一次开销都必须精打细算。在深度学习图执行引擎的紧凑循环里，每秒钟可能有上万次算子调用。

如果用哈希表：**计算字符串的 Hash 值 -> 内存随机跳跃 -> 处理哈希碰撞 -> 字符串比较**，这套流程下来，CPU 缓存命中率极差，白白烧掉了极其宝贵的纳秒级时间

所以，我们必须干掉哈希表，实现真正的物理 O(1) 分发！

### 方法：枚举掩码与连续内存数组

剥夺开发者使用字符串的权利。把张量的核心属性（如 Device）全部定义为底层的连续枚举（Enum）。 然后，把注册表从离散的哈希表，替换成**一块物理内存完全连续的定长数组**。 查表分发的过程，直接退化成**数组下标访问**，直接利用 CPU 的基址变址寻址，只需 1 条汇编指令！

```c++
#include <iostream>
#include <functional>
#include <array>
#include <stdexcept>
#include <cstdint> 

// ----- 系统规范 -----
enum class DeviceType : uint8_t {
    CPU = 0,
    CUDA = 1,
    NPU = 2,
    MAX_DEVICES // 自动获取枚举的总数（当前等于 3）
};

// 模拟 Tensor 数据结构
struct Tensor {
    DeviceType device;
    float data;
};

using OpFunc = std::function<Tensor(const Tensor&, const Tensor&)>;

// ----- 架构层 -----
// 极速算子注册表 (Fast Registry)
class FastOpRegistry {
private:
    //  淘汰 unordered_map，定义定长的连续数组
    // 强制转换为 size_t 作为数组长度。大括号 {} 会将内部全部初始化为 nullptr。
    std::array<OpFunc, static_cast<size_t>(DeviceType::MAX_DEVICES)> registry_{ nullptr };
    
    FastOpRegistry() = default;

public:
    FastOpRegistry(const FastOpRegistry&) = delete;
    FastOpRegistry& operator=(const FastOpRegistry&) = delete;

    static FastOpRegistry& get_instance() {
        static FastOpRegistry instance;
        return instance;
    }

    // 注册接口
    void register_op(DeviceType device, OpFunc func) {
        // 利用枚举强转作为数组下标，直接写入，速度达到物理极限
        registry_[static_cast<size_t>(device)] = func;
    }

    //  实现极速分发接口
    OpFunc get_op(DeviceType device) {
        size_t index = static_cast<size_t>(device);
        
        // 安全边界检查：防止业务端强转一个非法的非枚举数字进来导致数组越界
        if (index >= registry_.size()) {
            throw std::out_of_range("Device type index out of strict bounds.");
        }
        
        // 提取算子函数指针
        OpFunc op = registry_[index];
        
        // 判定是否为空（未注册）
        if (!op) {
            throw std::runtime_error("Operator not registered for this device type.");
        }
        
        return op;
    }
};

// 保留自动注册助手
class OpRegistrar {
public:
    OpRegistrar(DeviceType device, OpFunc func) {
        FastOpRegistry::get_instance().register_op(device, func);
    }
};

#define REGISTRY_CONCAT_IMPL(a, b) a##b
#define REGISTRY_CONCAT(a, b) REGISTRY_CONCAT_IMPL(a, b)

// 宏 API
#define REGISTER_FAST_OP(device, func) \
    static OpRegistrar REGISTRY_CONCAT(__op_reg_, __COUNTER__)(device, func);


// ----- 业务层测试 ----- 
Tensor add_cpu(const Tensor& a, const Tensor& b) {
    std::cout << "[Fast Backend] CPU Array Dispatch Success!" << std::endl;
    return Tensor{DeviceType::CPU, a.data + b.data};
}

// 自动注册
REGISTER_FAST_OP(DeviceType::CPU, add_cpu);

int main() {
    Tensor a{ DeviceType::CPU, 10.0f };
    Tensor b{ DeviceType::CPU, 20.0f };

    try {
        // 主框架的极速调用
        auto op = FastOpRegistry::get_instance().get_op(a.device);
        Tensor result = op(a, b);
        std::cout << "Result: " << result.data << std::endl;
    } catch (const std::exception& e) {
        std::cerr << "Fatal Error: " << e.what() << std::endl;
    }

    return 0;
}
```

## 常见面试题

针对 AI Infra 底层研发岗位（如 PyTorch、TVM、Triton 后端），面试官通常会从架构设计一路往下深挖到 C++ 编译链接层和预处理器机制

### 为什么 AI 框架底层（如 ATen）在分发算子时，强烈拒绝使用 `if-else` 或 `switch`？
为了实现**极端的架构解耦**，严格遵守**开闭原则**。AI 框架支持 CPU/CUDA/NPU 数十种异构硬件和多种数据类型，且第三方硬件迭代极快。如果使用 `if-else`，每次新增硬件都必须修改核心分发函数并重新编译整个框架的主分支。通过工厂注册表，第三方硬件团队只需编译出一个动态链接库（.so），由主进程在运行时动态加载，实现了底层硬件生态的“即插即用”。

### 你是如何实现“主框架代码完全不改，算子却能自动挂载”的？原理是什么？
利用 C++ 的**全局静态变量初始化机制**。C++ 运行时（C Runtime）会在跳转执行 `main()` 函数的第一条指令之前，扫描所有 `.o` 文件并自动调用所有全局静态对象的构造函数。我们将向哈希表插入算子的动作，封装在“注册助手类（Registrar）”的构造函数里。算子开发者只需在全局作用域定一个 Registrar 的静态对象，系统启动时就能利用底层的生命周期机制，神不知鬼不觉地完成自动建表。

### （高频）不同 `.cpp` 文件的全局静态变量初始化顺序是未定义的。如果你的静态 Registrar 在初始化时，OpRegistry 哈希表还没被初始化，程序不就崩溃了吗？如何解决？
这是 C++ 底层经典的 **静态初始化顺序灾难（Static Initialization Order Fiasco, SIOF）**。

绝对不能把 `OpRegistry` 设计成全局静态指针或全局静态变量。必须使用 **Meyers 单例模式**。在 `get_instance()` 内部，声明一个**局部静态变量**（`static OpRegistry instance;`）。C++11 标准在底层保证了：局部静态变量只会在执行流第一次经过它时安全初始化，并且编译器会自动加锁，保证其在多线程启动环境下的绝对线程安全。

### 在注册算子时，为什么一定要用 `#define` 宏来封装静态变量？定义拼接宏时，为什么必须嵌套内外两层？
**为什么要用宏**：如果让工程师手写静态变量，数千个算子极易发生变量名碰撞，导致编译期全局命名空间污染（Redefinition Error）。必须用预处理器的 `__COUNTER__` 或 `__LINE__` 生成绝对唯一的编号。

**为什么嵌套两层**：C++ 预处理器有一条铁律——如果宏参数被拼接符 `##` 直接修饰，那么该参数**不会被进一步宏展开**。如果只写一层宏，`__COUNTER__` 会被当作普通字符串字面量死死粘住，生成出无数个名叫 `__op_reg___COUNTER__` 的变量。只有通过嵌套一层 IMPL 辅助宏，利用间接调用，强制迫使 `__COUNTER__` 先展开成数字（如 `0`），再送入内层进行拼接，才能得到 `__op_reg_0`。

### （高阶性能题）`std::unordered_map` 的时间复杂度是 O(1)，但在真正的 PyTorch 底层，用它来做分发够快吗？工业界是怎么优化的？
**不够快，甚至很慢**。虽然哈希表理论上是 O(1)，但每次计算字符串（如 `"add_CPU_FP32"`）的 Hash 值、处理哈希碰撞、以及遍历红黑树/哈希桶的指针跳跃，在深度学习框架每秒上万次的算子调用（Tight Loop）中，会带来极高昂的 CPU 开销和 Cache Miss。

**工业界优化**：真实的 PyTorch Dispatcher 会将算子的硬件设备和数据类型压缩成一个紧凑的**枚举位掩码（DispatchKeySet / Bitmask）**。注册表在底层根本不是哈希表，而是扁平的**函数指针数组**。查表分发的过程，被极度简化为通过计算出的整数进行**数组索引访问（Array Indexing）**，将系统开销压榨到物理极限的几条汇编指令。
