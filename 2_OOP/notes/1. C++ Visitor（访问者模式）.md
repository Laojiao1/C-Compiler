# 1. C++ Visitor 与 Mutator

### 遇到的问题：编译器架构的灾难

假设你正在参与开发 TVM 或者 PyTorch 的底层（比如 TorchScript / FX）。深度学习模型在底层都会被解析成一棵抽象语法树（AST）或者 中间表示（IR）

假设我们只有最简单的三种节点（数据结构）：

- `VarNode` (变量，比如 x)
- `AddNode` (加法)
- `MulNode` (乘法)

一开始，你的任务只是把这棵树**打印**出来。 按照传统的 C++ 面向对象思维，你会怎么做？ 你会在基类 `Node` 里加一个虚函数 `virtual void print() = 0;`，然后去 `VarNode`、`AddNode`、`MulNode` 里分别实现它。这看起来很完美，对吧？

**灾难：** 第二天，老板说我们要加一个“类型推导（Type Check）”功能。你只能乖乖回到基类，加一个 `virtual void type_check() = 0;`，然后再把所有的子类全都改一遍。 第三天，又要加一个“常量折叠（Constant Folding）”优化 Pass... 第四天，又要加一个“算子融合（Operator Fusion）”Pass...

**问题：** 每一次增加新的操作（Compiler Pass），你都要去修改**所有**的底层数据结构代码。如果你的编译器里有 200 种算子节点，你为了加一个 Pass，要修改 200 个类的源码。这严重违反了**开闭原则（对扩展开放，对修改关闭）**，代码很快就会变成一坨无法维护的屎山

### 解耦的终极解法 —— Visitor（访问者模式）

在编译器的世界里，有一个明显的规律：

- **数据结构（AST 节点）是极其稳定的**：加法就是加法，乘法就是乘法，基本的算子种类很少变动
- **操作（Compiler Pass）是极其频繁变化的**：今天做算子融合，明天做显存分配，后天做 INT8 量化

**Visitor（访问者模式）的核心动机就是：将“操作（Pass）”从“数据结构（Node）”中彻底剥离出来**

使用了 Visitor 之后，你想加 100 个新的优化 Pass，AST 节点的代码**一行都不需要改**！你只需要写一个新类继承 `Visitor` 即可。这让编译器的各个模块（IR 结构 vs 优化逻辑）实现了完美的解耦。

### 底层核心机制（Double Dispatch / 双重分派）

很多人学 Visitor 觉得绕，是因为没懂 C++ 的底层分派逻辑

在 C++ 中，虚函数机制（vtable）只支持**单重分派（Single Dispatch）**。 也就是说，当你调用 `obj->func(arg)` 时，具体执行哪段代码，**仅仅取决于 `obj` 的运行时类型**，而**不取决于 `arg` 的运行时类型**。

此外，虚函数在高性能场景下会被嫌弃：

1. **指令缓存 (I-Cache) 未命中**：虚函数是间接跳转（Indirect Jump），CPU 没法提前把函数指令读入 Cache。
2. **分支预测 (Branch Prediction) 极易失败**：如果一个数组里混杂着各种不同的子类指针（`BaseOp*`），在一个大 `for` 循环里调用虚函数，CPU 的分支预测器会彻底懵逼，导致流水线频繁冲刷（Pipeline Flush），极其伤性能。
3. **无法内联优化 (Inlining)**：编译器在编译期不知道你要调哪个函数，所以绝大多数情况下无法把函数体直接嵌入代码，丢失了 C++ 最大的性能优化武器。

所以，我们需要用现代 Visitor 模式来替代传统的继承体系。它利用 C++ 模板在**编译期**完成类型分发，内存极其紧凑，且对 CPU Cache 极其友好，并且采用 Visitor 模式可以实现双重分派

> **Visitor 是如何用 C++ 巧妙实现双重分派的？**
>
> 它利用了两步“踢皮球”：
>
> 1. **第一脚（利用多态）**：把 Pass (Visitor) 作为一个指针 `v` 传给 Node 的 `accept(v)` 虚函数。这一步根据 Node 的运行时类型，跳到了具体的节点（比如 `AddNode`）里。
> 2. **第二脚（利用重载）**：在 `AddNode` 内部，只有一行极其关键的代码：`v->visit(this);`
>    - 此时 `v` 是个多态指针，决定了调用具体的哪个 Pass（比如 PrintPass）。
>    - 此时 `this` 的**编译期静态类型**就是精确的 `AddNode*`！所以 C++ 编译器会在 `v` 里直接精准匹配到参数为 `AddNode*` 的那个 `visit` 重载函数！
>
> 这套“反客为主”的组合拳，就是 Visitor 模式的本质，也是整个 TVM / PyTorch 底层 Pass 执行体系的基石

## 代码

```c++
#include <iostream>
#include <string>
#include <memory>
#include <unordered_map>

// 前置声明，告诉编译器有这几个数据结构
class VarNode;
class AddNode;

// ----- 架构层 -----

// 操作接口 (Visitor) ：所有 Compiler Pass 的基类
class IRVisitor {
public:
    // 针对不同类型的节点，提供精确的重载函数
    // 这里利用了 C++ 的函数重载（静态绑定），使得 Visitor 明确知道自己正在处理哪种具体节点
    // = 0 表示这是一个纯虚函数，派生类必须实现它
    virtual void visit(VarNode* node) = 0;
    virtual void visit(AddNode* node) = 0;

    // 虚析构函数，确保派生类对象被正确析构
    // = default 表示使用编译器生成的默认实现
    virtual ~IRVisitor() = default;
};

// 数据结构接口 (Node)：所有 AST 节点的基类
class ExprNode {
public:
    // 唯一向外暴露的操作入口。
    // 接受一个基类指针 visitor，并将其“引入”到自己的作用域
    virtual void accept(IRVisitor* visitor) = 0;

    virtual ~ExprNode() = default;
};

// ----- 实现层 ----- 
class VarNode : public ExprNode {
public:
    std::string name;
    
    // 这里使用 std::move 避免堆上字符串的拷贝开销，提高性能
    explicit VarNode(std::string n) : name(std::move(n)) {}

    void accept(IRVisitor* visitor) override {
        // 实现“踢皮球”机制：调用 visitor 的某个方法，并把当前对象的指针传给它
        visitor->visit(this);
        // 思考：为什么不能把这行代码写在基类 ExprNode 里的 accept 中，而必须在每一个子类（如 VarNode, AddNode）里“死板地”重复写一遍？
        // 因为 C++ 是静态类型语言，函数重载是在编译期决定的，如果直接写在基类中，编译器无法知道当前对象的实际类型，从而无法调用正确的 visit 方法。每个子类必须重写 accept 方法，以确保调用的是对应类型的 visit 方法，从而实现多态行为。
    }
};

class AddNode : public ExprNode {
public:
    // 采用 RAII 思想：使用 unique_ptr 独占子节点的所有权，防止多 Pass 遍历时的内存泄漏
    std::unique_ptr<ExprNode> lhs;
    std::unique_ptr<ExprNode> rhs;

    AddNode(std::unique_ptr<ExprNode> l, std::unique_ptr<ExprNode> r) 
        : lhs(std::move(l)), rhs(std::move(r)) {}

    void accept(IRVisitor* visitor) override {
        // 同上
        visitor->visit(this);
    }
};


// ----- 实现层：具体操作 (Concrete Visitor / Pass) -----
// 这是一个具体的 Compiler Pass，用于打印 IR 树
class PrintVisitor : public IRVisitor {
public:
    void visit(VarNode* node) override {
        // 叶子节点，到底了，直接触发动作
        std::cout << node->name;
    }

    void visit(AddNode* node) override {
        std::cout << "(";
        
        // 实现对左子树的递归访问
        // 思考：如何让左子树继续执行当前的 Print 逻辑？
        // 不要尝试去 cast 子节点的类型，而是把“当前正在执行的 Pass（即 this）”继续喂给子节点。
        node->lhs->accept(this);

        std::cout << " + ";
        
        // 实现对右子树的递归访问
        node->rhs->accept(this);

        std::cout << ")";
    }
};

// ----- 求值 Pass (Evaluate Visitor) -----
class EvaluateVisitor : public IRVisitor {
private:
    // 结果寄存器：每次 visit 执行完后，它的“返回值”就会暂存在这里
    int current_result_ = 0; 
    
    // 模拟运行时的变量环境 (Runtime Context)，用来充当“字典”或“内存”
    // 比如你的表达式是 x + y，AST 里只有变量的名字 "x" 和 "y"。当你要计算具体数值时，你必须查字典：env_ 里可能存着：{"x": 10, "y": 20}
    std::unordered_map<std::string, int> env_;

public:
    explicit EvaluateVisitor(std::unordered_map<std::string, int> env) 
        : env_(std::move(env)) {}

    // 对外暴露获取最终结果的接口
    int get_result() const { 
        return current_result_; 
    }

    void visit(VarNode* node) override {
        // 实现叶子节点（变量）的求值：去 env_ 里查变量的值，然后把它放进“寄存器” current_result_ 中
        // at 的作用是：用键（Key）去查找对应的值（Value）
        current_result_ = env_.at(node->name); // （为防崩溃，可以简单假设变量一定存在）
    }

    void visit(AddNode* node) override {
        // 实现加法节点的求值：需要左子树的值，和右子树的值，然后相加
        node->lhs->accept(this); // 递归访问左子树
        int left_value = current_result_; // 备份左子树的结果

        node->rhs->accept(this); // 递归访问右子树
        int right_value = current_result_; // 备份右子树的结果

        // 相加并写回寄存器
        current_result_ = left_value + right_value; 
    }
};

int main() {
    // 构造一棵 IR 树：(x + y)
    // 使用 std::make_unique 避免裸指针 new，确保这棵树在离开 main 作用域时，能沿着枝干从上到下安全、级联地析构，保证内存不会泄露
    auto x = std::unique_ptr<VarNode>(new VarNode("x"));
    auto y = std::unique_ptr<VarNode>(new VarNode("y"));
    auto tree = std::unique_ptr<AddNode>(new AddNode(std::move(x), std::move(y)));

    // 实例化我们的 Compiler Pass
    PrintVisitor printer;
    
    // 启动：把 Pass 喂给 AST 的根节点
    std::cout << "IR Tree: ";
    tree->accept(&printer);
    std::cout << std::endl;

    std::unordered_map<std::string, int> env = {{"x", 10}, {"y", 20}};
    EvaluateVisitor evaluator(env);
    tree->accept(&evaluator);
    std::cout << "Evaluate Result: " << evaluator.get_result() << std::endl;

    return 0;
}
```

## 进阶：实现常数折叠优化器 (Constant Folding Mutator)

在真正的 AI 编译器（如 TVM、PyTorch FX）中，有两大铁律是我们刚才没碰的：

**深度学习模型不是“树”，而是“有向无环图（DAG）”**

- 我们刚才用了 `std::unique_ptr`，它代表“独占所有权”。这在严格的“树”结构里是没问题的（一个子节点只能有一个父节点）。 但在深度学习里，一个张量 `x` 可能被同时用在很多地方，比如 `(x + y) * x`。此时 `x` 节点有两个父节点（加法和乘法）。如果你用 `unique_ptr`，系统立马崩溃，因为同一块内存不能被独占两次！ **架构破局**：在 AI 编译器底层，AST 节点必须使用共享所有权机制（即 `std::shared_ptr` 或侵入式引用计数 `IntrusivePtr`）

**编译器不做“只读”，全是在“改写”**

- 我们刚才只是把树遍历了一遍（Print 和 Evaluate）。但在编译期，最核心的动作是 **优化（Optimization Pass）**，比如把 `x + 0` 这个毫无意义的算子直接踢出图，替换成单节点 `x`。 这意味着我们的 Visitor 不能再返回 `void`，它必须返回一个新的、被修改后的节点指针！这被称为 **IRMutator（中间表示改写器）**。

```c++
#include <iostream>
#include <string>
#include <memory>

class VarNode;
class AddNode;
class ExprNode;

// 用别名简化 shared_ptr 的书写
using Expr = std::shared_ptr<ExprNode>;

// ----- 架构层 -----
// 改写接口 (IRMutator)
class IRMutator {
public:
    virtual ~IRMutator() = default;

    // 核心变动：visit 必须返回 Expr，允许在遍历过程中替换节点
    virtual Expr visit(VarNode* node) = 0;
    virtual Expr visit(AddNode* node) = 0;
};

// 数据结构接口 (Node)
class ExprNode : public std::enable_shared_from_this<ExprNode> {
public:
    virtual ~ExprNode() = default;
    virtual Expr accept(IRMutator* mutator) = 0;
};


// ----- 实现层 ----- 
// 具体数据结构
class VarNode : public ExprNode {
public:
    std::string name;
    explicit VarNode(std::string n) : name(std::move(n)) {}

    Expr accept(IRMutator* mutator) override {
        return mutator->visit(this);
    }
};

class AddNode : public ExprNode {
public:
    Expr lhs;
    Expr rhs;
    AddNode(Expr l, Expr r) : lhs(std::move(l)), rhs(std::move(r)) {}

    Expr accept(IRMutator* mutator) override {
        return mutator->visit(this);
    }
};


// 常量折叠优化 Pass (Constant Folding)
class ConstFoldingMutator : public IRMutator {
public:
    Expr visit(VarNode* node) override {
        // 叶子节点，一般不需要改写，直接返回它自己。
        return node->shared_from_this();
    }

    Expr visit(AddNode* node) override {
        // 递归改写左子树和右子树
        // 核心思想：自底向上。必须先把底层的子节点优化干净，再来处理当前层。
        Expr optimized_lhs = node->lhs->accept(this);
        Expr optimized_rhs = node->rhs->accept(this);

        // 核心优化逻辑 (X + 0 -> X)
        // 使用 dynamic_pointer_cast 在运行时进行“模式匹配”
        if (auto rhs_var = std::dynamic_pointer_cast<VarNode>(optimized_rhs)) {
            // 如果右子树是一个 VarNode，并且名字是 "0"
            if (rhs_var->name == "0") {
                // 触发常数折叠：直接丢弃 AddNode 和 0，把左子树“提拔”上来
                return optimized_lhs;
            }
        }

        // 如果没有触发优化规则（比如是 x + y，或者 x + 1）
        // 则用优化过的左右子树，重新组装出一个新的 AddNode 返回
        return std::make_shared<AddNode>(optimized_lhs, optimized_rhs);
    }
};

int main() {
    // 构造 DAG：计算图 (x + 0)
    Expr x = std::make_shared<VarNode>("x");
    Expr zero = std::make_shared<VarNode>("0");
    Expr graph = std::make_shared<AddNode>(x, zero);

    ConstFoldingMutator optimizer;
    
    // 执行优化 Pass
    Expr optimized_graph = graph->accept(&optimizer);

    // 验证结果：如果优化成功，optimized_graph 应该直接指向 VarNode("x")
    if (auto var = std::dynamic_pointer_cast<VarNode>(optimized_graph)) {
        std::cout << "Optimization Success! Remaining Node: " << var->name << std::endl;
    } else {
        std::cout << "Optimization Failed! Not folded." << std::endl;
    }

    return 0;
}
```

## 面试题

关于 Visitor 和 Mutator 的高频硬核面试题通常围绕“分派机制”、“内存安全”和“系统开销”展开：

### 什么是“双重分派”？C++ 的虚函数为什么只能做单重分派？
C++ 的虚函数（vtable 机制）只能做单重分派，即函数调用的具体实现**仅仅依赖于 `this` 对象的动态类型**，与传入参数的运行时类型无关。但在编译器中，我们需要根据“Pass（操作）”和“Node（数据结构）”两者共同决定执行逻辑

Visitor 解决方式：

- 第一步，利用 `node->accept(visitor)` 触发虚函数调用（第一次动态分派，跳入具体的 Node）
- 第二步，在 `accept` 内部执行 `visitor->visit(this)`

此时 `this` 的**静态类型（Static Type）**被锁定，编译器在编译期就会强制匹配 Visitor 中对应的重载函数。两者结合打出双重分派

### 为什么要用 Visitor 模式来遍历 AST？它解决了什么问题？
为了严格遵守 **开闭原则（Open-Closed Principle）**。编译器的 AST 节点（数据）极度稳定，而 Compiler Pass（操作）极其多变。如果将 Pass 塞进 Node 作为虚函数，每次新增 Pass 都会导致所有 Node 类的源码被修改和重新编译。Visitor 将“操作”从“数据”中抽离，新增 Pass 只需编写新的 Visitor 子类，彻底封死了 Node 代码的修改

### 标准 Visitor 的 `visit` 是 `void` 签名，如何实现需要返回值的 Pass（如类型推导/求值）？
有两种手段：
- **状态寄存器（面向对象做法）**：在 Visitor 类内部定义成员变量暂存结果。子节点执行完毕后，将结果写入寄存器，父节点直接读取。（你刚才手写的 `EvaluateVisitor` 就是这种方式）
- **泛型/类型擦除（现代 C++）**：将 Visitor 改写为模板类 `template <typename R>`，强制 `visit` 返回 `R`；或者直接返回 `std::any` 进行运行时拆包

### 深度学习编译器的 IRMutator 中，为什么必须用 `shared_ptr`（或侵入式指针）而不是 `unique_ptr`？
传统的编译器 AST 是一棵“树”，节点关系严格遵循“一对多”，可以用 `unique_ptr` 表达独占所有权。但深度学习的计算图是**有向无环图（DAG）**，一个 Tensor 节点（如输入 x）可能同时被传给多个算子，它拥有多个父节点。如果在 DAG 中强制使用 `unique_ptr`，必定导致多重析构或所有权转移失败，造成系统崩溃。必须引入共享所有权机制

### Visitor 模式的系统开销（Overhead）在哪里？工业界如何优化？
- **虚函数开销**：`accept` 和 `visit` 强制走虚表查找（VTable Lookup），打断了 CPU 指令流水线，且几乎无法被编译器内联（Inline）
- **缓存未命中（Cache Miss）**：AST 节点通常通过 `new` 或 `make_shared` 在堆上碎片化分配，指针跳跃遍历时会导致 CPU Cache 严重缺失
  - **实际采用的优化方案**：在 LLVM / TVM 源码中，通常使用 **CRTP（奇异递归模板模式）** 配合静态多态来干掉虚函数；同时使用**内存池（Memory Arena / Bump-pointer Allocator）**集中分配节点，确保内存物理连续性
